# 增量同步与 Lint

![[assets/03-04-sync-and-lint-illustrations/01-sync-lint-hero.excalidraw]]

> [!note]
> 真正会长期使用的个人知识库，绝不是“一次性搭好就结束”的系统。它需要一边吸收新资料，一边发现旧问题。增量同步负责让它继续长，Lint 负责防止它慢慢烂掉。

## 1. 为什么不能每次都全量重建

刚开始做知识系统时，很多人会默认一种最直觉的方案：

> 每次新增了一点资料，就把整个库重新扫一遍、重建一遍。

这在很小的 demo 里没问题，但资料一多就会出现明显问题：

- 成本高
- 时间长
- 重复工作多
- 旧页面容易被静默改坏
- 人工确认过的内容容易被覆盖

更重要的是，个人知识系统本来就是长期演化的。

所以更合理的方式通常不是“每次重建世界”，而是：

> 只识别本次新增或变化的原始资料，再只更新受影响的那部分 Wiki。

## 2. 增量同步到底在同步什么

增量同步不是简单地“把新文件扫进去”，而是把变化从 Raw 层逐步传递到 Wiki 层。

它主要回答几个问题：

- 哪些原始笔记是这次新增或发生变化的
- 这些变化会影响哪些已有 Wiki 页面
- 是更新旧页面，还是确实应该新建页面
- 哪些结论需要追加，哪些结论需要保留冲突

所以同步的对象，不只是文件本身，而是文件引发的知识变化。

## 3. 一个最小可用的同步流程

一个比较稳的增量同步流程，通常像这样：

1. 确定本次变化范围
2. 读取系统入口页和相关 Wiki 页面
3. 搜索已有 Wiki，优先更新旧页
4. 从原始资料里提取概念、项目、决定、模式
5. 写回受影响的 Wiki 页面
6. 更新索引页、总览页和变更日志

这个“优先更新旧页”特别重要。

因为很多知识库最后不是坏在“没写进去”，而是坏在“同一个概念被写成了三四份相似页面”。

## 4. 为什么“优先更新旧页面”比“不断新建页面”更重要

个人知识系统不是资讯站点，不是每次有新来源都应该新开一页。

真正更有价值的，往往是：

- 同一个概念持续长在同一页里
- 同一个项目的状态被不断更新
- 同一个决定有时间上的前因后果

这意味着同步时要优先问：

> 这条新资料，是在扩展哪个已有节点，而不是“我能不能再新建一个页”。

只有当主题真的独立、现有页确实装不下时，才适合新建。

## 5. 冲突、过期和时间变化应该怎么处理

个人知识库不是静态百科，它会不断遇到这些情况：

- 旧结论被新资料推翻
- 不同时期的判断互相矛盾
- 某个项目在半年前和现在完全不是一个状态

这时候最糟糕的做法，是把旧内容悄悄覆盖掉。

更稳的处理方式通常是：

- 保留时间信息
- 标清来源
- 说明“这是旧说法”还是“这是更新后的判断”
- 证据不够时明确写“待核实”

也就是说，知识系统不只是保存“最新说法”，也要保存“它怎么变成现在这样”。

## 6. Lint：知识库的体检系统

同步解决的是“继续长”，Lint 解决的是“别长歪”。

一个实用的 Wiki Lint，通常会检查这些问题：

- 没有入链或出链的孤立页面
- 缺少原始来源的结论
- 同义、重复或互相矛盾的页面
- 失效的双链和无效 YAML
- 新来源已经使旧结论过时的内容
- 被多次提到但尚未建立页面的重要概念

你可以把 Lint 理解成：

> 它不负责写新知识，但负责提醒你“这里已经开始腐烂了”。

## 7. 自动化能做什么，人工又该保留什么

增量同步和 Lint 都很适合自动化，但自动化不等于全自动放权。

通常更合理的边界是：

- 程序自动发现变化范围
- Agent 自动读取相关来源并给出更新建议
- 系统自动做基础 Lint
- 人工对关键页、冲突页和高价值结论保留最终判断

特别是 `status: reviewed` 这类人工确认过的页面，更不适合被静默重写。

## 8. 让知识库可持续的关键，不是“更聪明”，而是“更克制”

很多人会把同步系统想成一个越来越聪明的自动编辑器。

但长期来看，一个健康的知识库维护系统更像一个克制的编辑助手：

- 它知道该更新哪里
- 知道哪些内容先别乱改
- 知道证据不够时该停下
- 知道什么时候只是提示问题，而不是直接替你做判断

这是为什么同步和 Lint 看起来没有“会回答问题”那么炫，但它们反而决定了知识系统能不能活得久。

## 9. 这篇先记住五个结论

1. 个人知识库不适合每次都全量重建，更适合按变化范围做增量同步。
2. 同步的核心不是“扫新文件”，而是“把知识变化合并到受影响的页面”。
3. 优先更新旧页面，通常比不断新建新页面更有价值。
4. 冲突和时间变化最好保留，而不是悄悄覆盖。
5. Lint 是知识库的体检系统，负责发现孤岛、重复、失效和来源缺失等长期问题。

## 10. 下一步

当知识库已经有分层、有 Wiki、也有持续维护机制后，下一步才轮到一个真正关键的问题：[[03.05-接入 Codex、Claude Code 等 Agent]]。

因为只有当 Agent 知道该先读什么、去哪里搜、什么时候回原文核验，这套知识系统才算真正能被用起来。
