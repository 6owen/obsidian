# 需求与边界

![[assets/03-01-needs-boundaries-illustrations/01-needs-boundaries-hero.excalidraw]]

> [!note]
> 很多人以为“我已经写了很多笔记”，下一步只要接个模型就能得到一个聪明的个人助手。但真正开始做时，第一道坎往往不是模型，而是：这些资料到底能不能被稳定使用。

## 1. 为什么“有很多资料”还不等于“有个人知识库”

很多人的个人资料其实已经很多了：

- Obsidian 笔记
- 项目代码
- 零散的 Markdown 文档
- 收藏的网页、PDF、截图
- 任务记录、日报、复盘

从数量上看，东西并不少。

但一旦你真的想让 Agent 用这些资料做事，很快就会发现一个问题：

> “资料很多”只是存量概念，“知识库可用”才是系统概念。

也就是说，东西在，不代表系统就能稳定回答。

最常见的断层有这些：

| 表面上已经有了 | 实际缺的是什么 |
| --- | --- |
| 很多笔记 | 不知道哪篇是权威版本 |
| 很多文件 | 没有统一入口，不知道从哪里查 |
| 很多历史记录 | 缺少结构化摘要和来源链接 |
| 很多个人经验 | 没有沉淀成可复用的规则 |
| 很多上下文 | 没有办法在一次调用里只拿到最相关部分 |

所以个人知识库的第一步，不是继续囤资料，而是先承认：

> 笔记系统解决“我能写下来”，知识系统解决“我和 Agent 之后还能稳定用起来”。

## 2. 个人知识库到底想解决什么

如果只用一句话概括，个人知识库想解决的是：

> 让我的资料对未来的我、以及对 Agent，都变得更容易找到、理解、引用和维护。

这里至少包含四个目标。

### 2.1 找得到

当问题出现时，系统要能尽快定位相关材料。

比如：

- “我以前写过关于 RAG 评测的结论吗？”
- “这个项目上次为什么改成这个方案？”
- “我对某个工具的偏好，之前在哪篇记录里提过？”

如果每次都只能靠全文搜索和手动翻找，那还不算真正可用。

### 2.2 看得懂

原始资料往往是为“当时的自己”写的，不一定适合给未来的自己或 Agent 直接使用。

所以系统需要一些中间层，帮助完成这些事情：

- 给笔记提供主题入口
- 把零散事实整理成概念、项目、决定
- 让一段记录可以被放回更大的上下文里理解

这就是为什么后面要引入 Wiki 层，而不是只做全文检索。

### 2.3 能追溯

对 Agent 来说，“说得像”不够，最好还能回答：

- 这个结论来自哪里
- 是原始事实、个人观点，还是 AI 推断
- 如果我不信，能不能回到原文核验

没有追溯能力的知识系统，很容易越用越虚。

### 2.4 能长期维护

个人知识库不是一次性搭完的工程，而是一个长期演化的系统。

所以它必须支持：

- 新笔记进入系统
- 旧结论被更新
- 重复内容被合并
- 冲突结论被保留并标明时间

否则系统只会在演示那几天看起来漂亮，后面很快失效。

## 3. 这一章不想做成什么

要把边界讲清，最有效的方法往往不是只说“要做什么”，而是同时说清“不做什么”。

个人知识库通常不应该被误解成下面这些东西。

### 3.1 不是“把一切都塞进模型”

很多人做第一版时会自然地想：

> 我把所有笔记都喂给模型，它不就什么都知道了吗？

问题在于：

- 成本会很高
- 噪音会很多
- 相关性会很差
- 更新会很麻烦

更关键的是，模型本身是无状态的。

所谓“它知道了”，本质上只是因为你在本次调用里，把相关材料重新喂给了它。喂得准，它就像知道；喂得乱，它就像糊涂。

所以知识系统的重点不是“全塞”，而是“按需、按层、按边界地喂”。

### 3.2 不是“只有向量库就够了”

向量检索很重要，但它只是解决“相似内容怎么召回”。

它解决不了所有问题，比如：

- 哪条结论是人工确认过的
- 这份资料是不是敏感内容
- 两篇笔记说法冲突时该怎么处理
- 一个结论能不能回到具体原文

所以“个人知识库 = 向量数据库”这个理解太窄了。

真正可用的系统至少还要有：

- 原始层
- 索引层
- 派生知识层
- 受控记忆层

### 3.3 不是“让 AI 自动改写一切原文”

原始笔记的价值，在于它保留了当时的上下文、情绪、判断和细节。

如果一上来就让 AI 大面积改写、归并、重写原文，代价通常很大：

- 原始证据被冲淡
- 用户自己的写作习惯被打断
- 后续追溯变困难

所以更合理的方式通常是：

- 原始资料继续保留在原位置
- AI 在旁边建立派生层
- 派生层始终指回原始来源

这也就是后面要讲的 LLM Wiki 思路。

## 4. 先定义你的数据源边界

一个个人知识系统，如果范围无限，最后通常什么都做不好。

所以要先明确：这套系统到底打算覆盖哪些资料。

常见的数据源可以这样分：

| 数据源 | 典型内容 | 建议定位 |
| --- | --- | --- |
| Obsidian 笔记 | 想法、记录、学习笔记、项目过程 | 核心原始资料层 |
| 本地文档 | Markdown、PDF、方案、简历 | 补充资料层 |
| 代码仓库 | 代码、README、提交上下文 | 与项目知识强相关 |
| 网页资料 | 官方文档、博客、新闻 | 外部参考，不一定长期沉淀 |
| 即时对话 | 聊天记录、临时讨论 | 不一定全部保留，需筛选沉淀 |

这里最重要的不是“资料越多越好”，而是：

> 哪些内容是你的长期知识来源，哪些只是临时参考。

如果这个边界不清，后面检索时就会出现两个问题：

- 召回很多不该长期信任的内容
- 系统把临时噪音误当成长期结论

## 5. 再定义隐私和权限边界

只要资料开始被 Agent 读取，权限问题就不能再放到最后想。

个人知识库里常见的敏感内容包括：

- 密钥、账号、Cookie、Token
- 简历、合同、财务资料
- 聊天记录、私人判断、他人隐私
- 还没公开的项目方案或商业想法

所以你至少要回答几个问题：

1. 哪些目录默认允许检索？
2. 哪些目录只能手动指定后再读取？
3. 哪些内容只允许摘要，不允许全文进入上下文？
4. 哪些结论允许被写进 Wiki，哪些只能停留在原始层？

这不是“安全团队才需要想的事”，而是个人知识库从第一天就该有的边界意识。

## 6. 要先想清楚评测问题，而不是最后再补

很多知识库项目容易出现一个错觉：

> 只要能搜到东西、模型能说出一段像样的话，系统应该就差不多了。

但真正的可用性，最好一开始就问几个更硬的问题：

- 它能不能找对资料？
- 它能不能回到原始来源？
- 它会不会把旧结论当成新事实？
- 它会不会把观点说成事实？
- 它会不会把不该读的内容带出来？

换句话说，个人知识库也需要自己的“验收标准”。

最小的一组评测问题可以是：

| 问题 | 你想验证什么 |
| --- | --- |
| 能否找到相关原始笔记 | 检索入口是否有效 |
| 能否输出来源链接 | 追溯链路是否存在 |
| 能否区分事实、观点、推断 | 知识组织是否清晰 |
| 新笔记加入后能否反映到回答中 | 增量更新是否有效 |
| 遇到敏感资料时是否能正确收敛 | 权限边界是否工作 |

## 7. 一个更实用的目标：先做“可靠”，再做“聪明”

做个人知识系统时，一个特别常见的误区是太早追求“很像一个全能助理”。

但在真正可用之前，更重要的通常是这些基础能力：

- 能稳定找到正确材料
- 能标清来源
- 能回原文核验
- 能知道自己不知道
- 能在资料更新后继续保持一致

也就是说，第一阶段最值得追求的不是：

> “它看起来多聪明。”

而是：

> “它是不是足够可靠，可靠到我愿意真的把资料交给它参与工作。”

## 8. 这篇先记住五个结论

1. 有很多资料，不等于已经有了可用的个人知识库。
2. 个人知识库解决的不只是“存”，更是“找、懂、追溯、维护”。
3. 它不是把所有内容都塞进模型，也不是只做一个向量库。
4. 原始资料、派生知识和 Agent 可见内容，最好分层管理。
5. 设计知识库时，要尽早定义数据源、权限边界和评测问题。
