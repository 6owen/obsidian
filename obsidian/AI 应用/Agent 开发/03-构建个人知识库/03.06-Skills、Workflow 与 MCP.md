# Skills、Workflow 与 MCP

![[assets/03-06-skills-workflow-mcp-illustrations/01-skills-workflow-mcp-hero.svg]]

> [!note]
> 当知识库已经能被 Agent 使用后，下一步自然会出现一个问题：很多方法和动作会反复发生。那它们应该只是“每次临场发挥”，还是应该被封装成可复用能力？这一篇就是来分清 Skills、Workflow 与 MCP 的边界。

## 1. 为什么知识系统最终会走向能力封装

当你开始长期使用个人知识库，很快就会发现有些动作不断重复：

- 先读入口页
- 先查 Wiki，再回原文
- 新笔记进入后更新已有页面
- 检查来源缺失、失效双链和重复页面

如果每次都完全靠模型临场决定，系统当然还能工作，但会有几个问题：

- 表现不稳定
- 同样的问题每次都重新想一遍
- 好做法不容易沉淀下来

所以知识系统往上走一步，通常就会开始封装能力。

## 2. Skills：把好方法沉淀成可复用规则

Skill 更像一种可复用的方法包。

它适合承载的是：

- 这类任务应该怎么做
- 先后顺序是什么
- 哪些坑要避开
- 什么时候停下来要求证

在个人知识系统里，典型适合写成 Skill 的内容包括：

- 查询个人知识库的读取顺序
- 同步 Wiki 时的更新原则
- 检查来源、双链、状态的自检清单

所以 Skill 的关键词是：

> 方法、规范、边界、经验。

它不是在保存数据，而是在保存“做这件事时应该怎样做”。

## 3. Workflow：把高频流程做成确定性的骨架

如果 Skill 更像方法论，那 Workflow 更像可执行流程。

它适合解决的是：

- 哪些步骤应该固定
- 哪些步骤可以自动化
- 哪些地方需要重试、暂停、审批、恢复

例如在知识系统里，一个很自然的 Workflow 可能是：

1. 找出最近修改的原始笔记
2. 定位受影响的 Wiki 页面
3. 生成更新建议
4. 跑基础 Lint
5. 输出变更报告

这种场景的重点不是开放式推理，而是流程稳定、可重复、可恢复。

## 4. MCP：把外部能力和数据源接成标准接口

MCP 的位置又和前两者不一样。

它更像一个统一的对外连接层，让 Agent 能通过标准协议访问外部工具和数据源。

在个人知识系统里，MCP 适合承载的常见东西包括：

- 文件读取和目录搜索
- 数据库查询
- 第三方文档源
- 需要权限控制的外部系统

可以把它理解成：

- Skill 告诉你“怎么做”
- Workflow 告诉你“按什么流程做”
- MCP 告诉你“可以连到哪些外部能力去做”

## 5. 这三者最容易被混淆的地方

很多人第一次做时，容易出现三种混用：

### 5.1 把 Skill 写成工具说明书

如果一个 Skill 里只是在列工具参数，而没有方法和边界，它其实更像工具文档，而不是 Skill。

### 5.2 把 Workflow 当成开放式 Agent

如果一个流程本来就应该固定执行顺序，却全部交给模型自由发挥，系统通常会变得不稳定、难复盘。

### 5.3 把 MCP 当成业务权限系统

MCP 负责连接能力，但它不天然替代你对读写边界、敏感目录、审批规则的业务判断。

## 6. 在个人知识库场景里，分别适合封装什么

可以先用一个简单对照来记：

| 能力 | 在个人知识库里更适合封装什么 |
| --- | --- |
| Skill | 查询规则、同步规范、核验原则、Lint 清单 |
| Workflow | 增量同步流程、体检流程、发布前检查流程 |
| MCP | 文件系统、搜索接口、数据库、外部知识源 |

只要这个分工清楚，系统就会更容易演化。

## 7. 真正想留下来的，不是“会一次”，而是“下次还能稳定复用”

知识系统走到这里，重点已经不只是“这次能不能答对”，而是：

- 下次遇到相似任务，能不能沿用好方法
- 好的读取路径能不能沉淀下来
- 好的同步流程能不能重复跑
- 对外部能力的接入能不能保持一致

所以 Skills、Workflow 与 MCP，本质上是在把“个人知识系统的使用经验”继续向上抽象。

## 8. 这篇先记住五个结论

1. 当知识系统开始长期使用后，很多高频动作都值得进一步封装成能力。
2. Skill 更适合沉淀方法、规范和边界。
3. Workflow 更适合承载顺序明确、可重复、可恢复的流程。
4. MCP 更适合把外部数据源和工具接成标准接口。
5. 把这三者分开，知识系统才更容易复用、扩展和维护。
