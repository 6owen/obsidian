# 为什么很多 RAG Demo 一上生产就翻车

> [!note]
> 很多人第一次接触 RAG，都会先被一个漂亮 demo 打动：导几份文档，接一个聊天框，问问题就能答。可一旦真的开始日常使用，系统就会暴露出完全不同的一面。这一篇先不急着讲实现，而是先把“为什么会翻车”这件事看明白。

## 1. 先看一个很常见的错觉

![[assets/02-02-rag-demo-production-illustrations/01-demo-vs-production-rag.svg]]

很多 RAG 项目第一次演示时，体验都不差。

比如你准备了几十份文档：

- 制度文件
- 产品手册
- 会议纪要
- API 文档
- 项目资料

然后做一条基础链路：

1. 把文档切成 chunk。
2. 生成 embedding。
3. 写进向量库。
4. 用户提问后检索 top-k。
5. 再把结果拼给模型生成答案。

这时你随手问几个问题：

- “公司的报销标准是什么？”
- “某个接口怎么鉴权？”
- “某份产品说明里有没有写这个功能？”

系统通常都能答出点东西。

于是一个很常见的错觉就出现了：

> 只要把文档导进去，再接一个大模型，我就已经拥有知识库了。

问题在于，demo 阶段的问题往往都太干净了。

- 提问的人知道答案大概在哪。
- 用词和文档里的写法比较接近。
- 问题通常只涉及一份文档或一个局部事实。
- 很少碰权限、更新、冲突和历史版本。

而真正使用时，情况会立刻变复杂。

## 2. 真正使用时，问题会怎么冒出来

一旦进入真实场景，RAG 最常见的翻车方式通常有这几类。

### 1. 用户说法和文档说法对不上

用户问的是：

- “新人出差住酒店能报多少？”

但文档里写的是：

- “差旅住宿标准”
- “按城市级别执行”
- “特殊情况走审批流程”

如果系统只会做非常表面的相似度匹配，它就可能：

- 找不到正确材料
- 找到一堆相关但不够回答的问题
- 把“住宿标准”误答成“报销流程”

### 2. 正确答案分散在多份材料里

有些问题不是一段文档能答完的。

比如：

- “上季度客户最关心什么？”
- “这个问题为什么最近反复出现？”
- “某个报错到底该看文档、历史 issue 还是代码注释？”

这类问题通常需要：

- 跨多份会议纪要汇总
- 对照路线图和版本变化
- 从文档、代码、日志里拼出完整线索

单次检索、单次生成，常常根本不够。

### 3. top-k 里有看起来像答案的噪音

RAG 一个特别常见的假象是：

> 系统确实召回了一些“相关内容”，但这些内容并不等于“足够回答”。

比如你问“报销流程”，它可能召回：

- 差旅制度
- 财务审批规范
- 去年团建费用公示

前三者都和“报销”有关，但第三条只是语义上有点像，实际完全没用。可一旦把这些材料一起塞给模型，模型就可能在噪音里跑偏，最后给出一段看起来流畅、其实不可靠的回答。

### 4. 权限问题不是回答阶段才出现

这是很多团队最容易低估的一类问题。

假设知识库里有一份薪酬调整方案，只应该给少数人看。一个普通员工来问：

- “今年调薪幅度多少？”

如果你的系统是：

1. 先检索全库
2. 再从结果里删掉没权限的内容

那就已经晚了。

因为无权限内容很可能已经进入候选集，甚至已经进过模型上下文。权限不是最后一道补丁，而应该是检索阶段的输入条件。

### 5. 文档一更新，旧答案就开始失真

知识库还有一个现实问题：资料是会变的。

- 制度会更新
- 产品说明会改版
- 代码注释会过时
- FAQ 会被新版本替换

如果系统没有增量更新、版本追踪和重新评估机制，那它今天答对，不代表下周还答对。

## 3. 所以问题通常不在模型，而在系统底座

很多人遇到这些问题时，第一反应是：

> 要不要换一个更强的模型？

但大多数情况下，换模型只能让错误答案变得更顺。

因为真正的问题通常出在这些地方：

- 检索链路设计得不对
- chunk 颗粒不合适
- metadata 不完整
- 权限过滤加得太晚
- 文档更新机制缺失
- 没有评估集，不知道系统到底哪里坏了

也就是说，很多 RAG 项目失败，不是因为模型不够强，而是因为系统把“找资料”这件事做得不够可靠。

## 4. 一个能用的 RAG，至少要解决哪几层问题

如果把“导文档 + 向量检索 + 聊天框”看成最外层，那一个真正可用的 RAG，通常还至少包含下面这些层。

| 层 | 它负责什么 | 常见翻车点 |
| --- | --- | --- |
| 数据源边界 | 哪些资料应该进库，哪些不该进 | 一上来全塞进去，最后谁也调不明白 |
| 文档解析 | 结构、标题、表格、来源、时间怎么保留 | 只提纯文本，后面就失去上下文和可追溯性 |
| 清洗与切分 | chunk 颗粒是否完整、是否过碎或过大 | 太碎会丢条件，太大又会稀释相关性 |
| 检索策略 | 语义检索、关键词检索、metadata 过滤怎么配合 | 只靠向量，召不回编号、术语、代号 |
| 生成约束 | 回答是否基于证据、会不会承认不知道 | 模型自由发挥，把缺口补成幻觉 |
| 权限与安全 | 谁能看什么，什么时候拦截 | 检索后过滤，导致泄露或虚高召回 |
| 更新与评估 | 文档变了以后怎么同步、怎么知道系统变好还是变坏 | 没有评估集，只能靠感觉调参 |

从这个角度看，RAG 不是一个单点能力，而是一条链路。

只要这条链路里有一个关键环节不稳，最终回答就会开始漂。

## 5. 为什么“能回答”不等于“能用”

这是做 RAG 时最容易忽略的一点。

一个系统“能回答”，只说明：

- 模型看到了某些材料
- 输出了一段语言上通顺的结果

但“能用”意味着更多要求：

- 它找来的材料是对的
- 它没有漏掉关键限制条件
- 它不会把没权限的内容带出来
- 它知道资料不足时该停下来
- 它能说清来源来自哪里
- 文档更新以后它不会继续引用旧结论

所以从工程角度看，RAG 真正的目标不是“让模型更会说”，而是：

> 让模型在回答之前，先拿到对的、够用的、可引用的、权限正确的材料。

## 6. 这也是为什么 Part 02 不会直接从向量库开始讲

如果我们一上来就讲：

- 什么是 embedding
- 什么是向量相似度
- 什么是 ANN 索引

那当然也能讲通，但你很容易误以为：

> RAG 的核心就是向量检索。

其实不是。

向量检索当然重要，但它只是整个系统里的一层。真正决定 RAG 好不好用的，是整条链路能不能闭环：

- 找得准不准
- 找回来的东西能不能回答
- 回答能不能被核验
- 权限有没有守住
- 文档变化后系统会不会跟着变

所以接下来的 Part 02，我们不会按“概念字典”的方式写，而会按一条更贴近真实落地的路径走：

1. 先看为什么 demo 会翻车。
2. 再搭最小可运行 RAG。
3. 然后把检索能力一步步做扎实。
4. 再处理评估、更新、权限这些真正决定它能不能上线的问题。
5. 最后才讲什么时候该把它升级成 Agentic RAG。

如果把这件事再说得更直白一点，demo 和生产真正关心的问题根本不一样：

| 阶段 | 你最容易先问的问题 | 但真正该问的是 |
| --- | --- | --- |
| Demo | 能不能答出几句像样的话 | top-k 里到底有没有正确材料 |
| Demo | 模型会不会说人话 | 回答有没有证据、有没有边界感 |
| Demo | 页面顺不顺、交互好不好看 | 检索链路是不是稳定可解释 |
| Demo | 跑起来了没有 | 文档更新以后会不会继续答旧话 |
| Demo | 感觉好像更聪明了 | 有没有评估集证明它真的变好了 |

## 7. 这一篇先记住五个结论

1. 很多 RAG demo 能演示，不代表它已经是一个可靠知识系统。
2. 真实使用里的问题，往往不在模型，而在检索链路、chunk、权限、更新和评估机制。
3. top-k 里“看起来相关”不等于“足够回答”。
4. 权限必须在检索阶段生效，而不是生成前临时补一道过滤。
5. 一个可用的 RAG，不只是检索和生成，还必须解决来源、评估、更新和安全。
