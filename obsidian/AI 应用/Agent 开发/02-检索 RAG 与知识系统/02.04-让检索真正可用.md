# 让检索真正可用

![[assets/02-04-retrieval-quality-illustrations/01-retrieval-quality-hero.excalidraw]]

> [!note]
> 最小可运行 RAG 能跑通，不代表检索已经靠谱。真正开始日常使用以后，你会发现很多问题根本不是“系统没检索”，而是“它检索了，但没真的找对”。这一篇就是专门解决这个问题。

## 1. 只会向量检索，为什么很快就不够

最基础的 RAG 往往只有一层：

- 用户问题 → 向量检索 → top-k → 生成答案

这条链路在一些干净问题上能工作，但很快就会暴露三个典型问题：

### 1. 短问题没有足够语义

用户只问：

- “报多少”
- “怎么配”
- “27001”

这类问题本身信息量很低。

embedding 模型会尽量去理解它，但它能抓到的线索还是太少，所以很容易把一些“看起来都像”的内容一起召回来。

### 2. 精确词是向量检索的天然盲区

向量检索擅长语义相近，但对下面这些东西并不总是稳定：

- 编号
- 错误码
- 人名
- 产品代号
- 内部黑话

用户问的是精确名词，系统却只召回一堆“主题相近”的概述文档，这时模型再聪明也很难补回来。

### 3. top-k 里会混进语义噪音

很多召回结果不能说完全无关，但也并不能回答问题。

它们的问题是：

- 语义有点近
- 主题有点像
- 但并不是证据

一旦这些噪音和真正有用的材料一起被塞进上下文，模型就会更容易跑偏。

## 2. 所以检索增强的目标不是“更复杂”，而是“更少误判”

让检索真正可用，核心不是把系统变花，而是降低这三类误判：

- 该回来的没回来
- 不该回来的混进来了
- 回来的太散，模型抓不住重点

围绕这三个问题，最常见、也最有价值的增强通常是四类：

| 能力 | 它解决什么问题 |
| --- | --- |
| 查询改写 | 用户说得太短、太口语、太含糊 |
| 混合检索 | 语义相似和关键词精确匹配各有盲区 |
| 重排 | 候选池里有很多“像但没用”的噪音 |
| metadata 过滤 | 先缩小搜索范围，避免把不可能相关的材料也查进来 |

## 3. 查询改写：先把用户的话变成更适合检索的话

查询改写的本质不是“帮用户润色问题”，而是：

> 在检索前，把原始提问补成更适合搜索系统理解的版本。

比如用户问：

- “报多少”

系统真正需要检索的，可能是：

- “员工出差住宿费报销标准是多少”

或者用户问：

- “27001 怎么做”

系统更适合检索的是：

- “ISO/IEC 27001:2022 信息安全管理体系实施要求”

这一步的价值在于：它把口语问题、代词问题、对话上下文问题，先转成更稳定的检索输入。

但要注意一个边界：

> 改写是补充，不是替代。

原始问题最好仍然保留，并和改写版本一起参与检索。否则模型一旦把用户意思改偏，后面整条链路都会跟着偏。

## 4. 混合检索：不要把希望只押在一种相似度上

只做向量检索的问题是，它更像在问：

> 哪些文本语义上像这个问题？

而很多真实问题其实还在问：

> 哪些文本包含这个精确词？

所以更稳的做法通常是混合检索：

- 一路做语义检索
- 一路做关键词检索
- 最后再合并结果

这样做的好处是：

- 语义检索帮你抓近义表达
- 关键词检索帮你抓编号、术语、专有名词

你可以把它理解成：

> 一路负责“意思像不像”，一路负责“字面中不中”。

只有两路都看，盲区才会更小。

## 5. 重排：不是所有候选都该平等进入上下文

当你做完混合检索后，候选池通常会变大。

这时新的问题出现了：

- 候选变多了
- 但噪音也会一起变多

所以还需要一步重排。

重排要做的事不是“再召回一次”，而是：

> 在已经回来的候选里，再挑出真正最能回答问题的那几个。

这一步很重要，因为模型的上下文空间不是无限的。你不能把所有“有点像”的材料都喂进去，而应该尽量只喂：

- 最关键的证据
- 最少的噪音
- 最完整的几段上下文

换句话说，召回负责“别漏”，重排负责“别乱”。

## 6. metadata 过滤：先缩范围，往往比后面补救更有效

很多检索问题其实不需要靠更强模型解决，而是可以靠更早的范围约束解决。

比如你已经知道问题是：

- 某个产品的文档
- 某个时间范围内的会议纪要
- 某个项目目录下的文件

那就没必要在全库里盲搜。

metadata 过滤的价值就在这里：

- 按来源过滤
- 按时间过滤
- 按章节过滤
- 按文档类型过滤
- 按权限过滤

这类过滤不是锦上添花，而是减少噪音最直接的一种办法。

## 7. 检索增强不是堆模块，而是逐个验证

做到这里，一个特别容易犯的错误是：

> 既然这些都有效，那我一次性全上。

但更稳的方式其实是逐个增强、逐个验证：

1. 先加查询改写，看 top-k 有没有明显改善。
2. 再加混合检索，看精确词问题是不是好转。
3. 再加重排，看噪音是不是下降。
4. 再加 metadata 过滤，看范围是不是更稳。

这样做的好处是，你始终知道：

- 现在这一步到底改善了什么
- 代价是什么
- 有没有副作用

否则你很容易得到一个“组件很多”的系统，却说不清为什么它有时更好、有时反而更坏。

## 8. 真正的目标不是“召回得多”，而是“召回得刚好”

检索质量最后想达到的，不是：

- 回来越多越好

而是：

- 该回来的回来
- 不该回来的不要混进来
- 回来之后模型刚好能据此回答

这也是为什么检索增强真正的衡量标准，不应该只是“系统更复杂了”，而应该是：

- 正确材料更常进入 top-k
- 候选池里的噪音更少
- 模型更少被无关内容带偏

## 9. 这篇先记住五个结论

1. 最基础的向量检索很快就会遇到短问题、精确词和语义噪音这三类问题。
2. 查询改写解决的是“用户说得不适合搜”，不是替用户换问题。
3. 混合检索的意义在于同时覆盖“语义像不像”和“字面中不中”。
4. 重排的任务不是多召回，而是从候选池里挑出真正能回答的证据。
5. 检索增强最重要的不是模块多，而是每一步都能被验证到底改善了什么。
