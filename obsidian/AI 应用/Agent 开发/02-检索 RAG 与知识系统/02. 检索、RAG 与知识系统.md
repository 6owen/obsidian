# 检索、RAG 与知识系统

这一部分想解决的问题是：模型很强，但模型参数里的知识，并不自动等于“我这次任务真正需要的知识”。

当任务开始依赖本地文件、私有资料、最新网页、团队文档、可追溯证据时，只靠参数知识就不够了。于是我们才会引入检索、RAG，以及更完整的知识系统。

## 本部分主线

你可以先把这一部分理解成一条逐层补知识的链路：

1. 模型参数里有很多常识和通用知识，但不一定新，也不一定刚好是你需要的。
2. 如果把所有资料都硬塞进 prompt，会很贵、很慢，而且容易把模型喂晕。
3. 所以我们需要先检索，再只把真正相关的材料喂给模型。
4. 但真正落地时，问题往往不是“有没有检索”，而是“有没有找对、能不能评估、会不会越权、文档更新后会不会失效”。
5. 所以一个能用的 RAG，不只是向量检索加聊天框，而是一整套检索、评测、更新、权限和追溯机制。
6. 当单轮检索不够时，系统才会继续演化成 Agentic RAG，让模型自己参与查询改写、补查和多步决策。
7. 再往上走，就不只是“搜文档”，而是开始建设一个长期可维护、可更新、可追溯的知识系统。

## 这一部分最想讲清什么

| 问题 | 结论方向 |
| --- | --- |
| 模型不是已经知道很多东西了吗？ | 知道很多，不等于知道这次任务需要的最新、私有、可验证知识。 |
| 为什么不能直接把所有资料都塞进上下文？ | 因为上下文窗口、成本、延迟和噪音都会成为问题。 |
| 为什么很多 RAG demo 演示时看起来聪明，日常却不可靠？ | 因为真正的难点在检索链路、知识颗粒、权限过滤、更新机制和评估，而不在模型会不会说话。 |
| RAG 的本质是什么？ | 不是“用了向量数据库”，而是“先检索相关证据，再基于证据生成回答”。 |
| 检索系统和知识系统一样吗？ | 不一样。检索系统解决“找”，知识系统还要解决结构、更新、权限、追溯和维护。 |
| Agent 和 RAG 的关系是什么？ | RAG 可以独立存在；Agent 则让检索变成可规划、可循环、可判断证据充分性的能力。 |
