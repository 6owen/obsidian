# RAG、Knowledge Base、Context、Memory 的边界

![[assets/02-08-boundaries-illustrations/01-boundaries-hero.excalidraw]]

> [!note]
> 到这里，Part 02 其实已经讲完了一条完整主线：为什么需要外部知识、为什么 demo 会翻车、怎么搭最小链路、怎么把检索做准、怎么评测更新、怎么守住权限、以及什么时候该上 Agentic RAG。最后这一篇做一件很重要的事：把这些词真正分清楚。

## 1. 为什么这些词总是容易说混

只要开始做 RAG，几个词几乎一定会反复出现：

- RAG
- Knowledge Base
- Context
- Memory

而且它们很容易在讨论里被互相代替。

比如有人会说：

- “把记忆塞进 RAG”
- “把知识库直接喂进上下文”
- “做个 memory，其实就是多一个向量库”

这些说法不能说完全错，但它们会把系统层级搅在一起。

更清楚的方式是：把这些词看成不同位置上的东西。

## 2. Context：模型这次调用真正看见的内容

Context 是最靠近模型的一层。

它指的不是系统里“理论上有”的所有信息，而是：

> 这一次调用里，模型真正看到了什么。

它通常包括：

- system prompt
- 当前用户问题
- 历史消息
- 检索回来的片段
- 工具调用结果
- 当前任务状态

所以 Context 的关键不在“存储”，而在：

- 相关不相关
- 精简不精简
- 有没有过期

也就是说，Context 是最终进嘴里的东西。

## 3. Knowledge Base：系统外部可被检索的知识存量

Knowledge Base 更像模型外面的知识仓库。

它通常包括：

- 文档
- 代码
- 笔记
- 网页
- 数据库
- FAQ

这些内容并不会一次性全部进入模型。

它们先存在外部系统里，等需要时再被检索、过滤、挑选，最后其中一小部分才进入 Context。

所以 Knowledge Base 关注的是：

- 存了什么
- 结构如何
- 能不能更新
- 权限清不清楚
- 能不能被检索到

换句话说：

> Knowledge Base 是候选知识池，不是模型当前上下文本身。

## 4. RAG：把知识池里的材料接进本次回答

RAG 不是一堆资料本身，而是一条过程：

1. 从外部知识池里检索相关材料
2. 把材料注入当前上下文
3. 基于这些材料生成回答

所以 RAG 更像一个“接入过程”，不是一个存储层。

你可以把它看成：

- Knowledge Base 负责存
- RAG 负责取并接进来
- Context 负责真正给模型看

这三者的位置是不同的。

## 5. Memory：跨调用保留下来的持续状态

Memory 又和前面三者不太一样。

它最关键的特点不是“知识”，而是“持续”。

Memory 更常见的内容包括：

- 用户偏好
- 历史选择
- 任务进度
- 已验证有效的策略
- 某些需要跨任务延续的事实

它和 Knowledge Base 的区别在于：

- Knowledge Base 更像资料库
- Memory 更像持续状态和经验层

它和 Context 的区别在于：

- Context 是这次看见的
- Memory 是可能被未来取回的

它和 RAG 的区别在于：

- RAG 是过程
- Memory 是被管理和被召回的一类长期内容

## 6. 为什么 Memory 不能被简单理解成“再来一个向量库”

这是一个特别常见的误区。

很多人一说 Memory，第一反应就是：

- 存聊天记录
- 做 embedding
- 下次相似检索

这当然能形成一种最粗糙的记忆，但它很快就会带来污染：

- 临时约束和长期偏好混在一起
- 模型猜错的中间结论也被长期保存
- 旧偏好、过期信息和新事实彼此冲突

所以真正的 Memory 系统，通常还需要：

- 写入门控
- 冲突处理
- 生命周期管理
- 召回编排

这也是为什么 Memory 往往会放到 Part 04 再展开，而不是直接塞进 RAG 章节里一笔带过。

## 7. 用一句话把四者关系串起来

如果非要用一句尽量简洁的话来记，可以这么理解：

- Knowledge Base：外部资料池
- RAG：把资料池里的相关内容接进来
- Context：模型这次真正看到的内容
- Memory：系统跨调用保留下来的持续状态

它们的关系大致是：

\`\`\`text
Knowledge Base / Memory
        ↓
     检索 / 读取 / 召回
        ↓
      进入 Context
        ↓
      模型生成回答
\`\`\`

如果再加上 Agentic RAG，就是：

- 模型自己也开始参与决定该检索什么、该不该继续补材料

## 8. Part 02 到这里真正讲完了什么

回头看这一整个 Part 02，其实我们讲清的是一条非常完整的链：

1. 模型参数知识不够，所以要引入外部知识。
2. 但外部知识不是一导入就有用，demo 很容易翻车。
3. 所以要先搭最小可运行链路。
4. 再把检索做准。
5. 再让系统可评估、可更新。
6. 再补上权限和追溯。
7. 最后才轮到 Agentic RAG。
8. 收尾时再把 RAG、知识库、上下文、记忆彻底分开。

也就是说，这一部分真正完成的是：

> 把“模型如何使用参数之外的知识”这件事，从概念、系统、工程到边界，整体走了一遍。

## 9. 这篇先记住五个结论

1. Context 是模型这次真正看见的内容，不是系统里所有可用信息。
2. Knowledge Base 是外部知识存量，不等于当前上下文。
3. RAG 是把外部知识接入本次回答的一条过程，而不是一个存储层。
4. Memory 是跨调用保留下来的持续状态，和资料库不是同一种东西。
5. 把这几个词分开，后面做个人知识库和个人 Agent 时，系统边界会清楚很多。
