# 从最小可运行 RAG 开始

![[assets/02-03-minimal-rag-illustrations/01-minimal-rag-pipeline.svg]]

> [!note]
> 上一篇我们先把“为什么很多 RAG demo 会翻车”说清楚了。这一篇开始真正搭链路，但目标不是一口气做成生产系统，而是先做一个最小可运行版本：能入库、能检索、能生成、能带引用。

## 1. 为什么先做最小可运行版

很多人一做 RAG，就容易直接冲向一个很大的目标：

- 支持所有文档格式
- 接所有知识源
- 上混合检索
- 上 rerank
- 上 Agent
- 上权限系统

这条路的问题是，你会很快失去判断力。

因为一旦链路太长，系统答不好时你根本不知道问题出在哪：

- 是解析错了？
- 是 chunk 太碎？
- 是 embedding 不行？
- 是向量检索没召回来？
- 还是模型拿到材料后自己说跑偏了？

所以更好的做法是，先让系统具备一个最小闭环：

1. 读入一批边界清楚的文档。
2. 切成可检索的 chunk。
3. 把 chunk 写入索引。
4. 用户提问后找回 top-k。
5. 把找到的材料交给模型生成答案。
6. 在答案里附上引用。

只要这一条能跑通，你就已经有了一个可以继续调优的底座。

## 2. 最小可运行 RAG 到底最少包含什么

如果先不考虑“生产级”，一个最小可运行 RAG 通常只需要 7 个环节：

| 环节 | 作用 | 现在先做到什么程度 |
| --- | --- | --- |
| 数据源 | 决定读哪些资料 | 先选一个窄场景 |
| 文档解析 | 把原文变成结构化文本 | 先保留标题、段落、来源 |
| 切分 | 把长文拆成可检索颗粒 | 先做到大致完整，不追求最优 |
| Embedding | 把文本映射成向量 | 先选一套能稳定使用的模型 |
| 索引与存储 | 保存 chunk 与 metadata | 先能查，再谈扩展性 |
| 检索 | 根据问题找回相关材料 | 先做 top-k 检索 |
| 生成 | 基于材料回答并带引用 | 先固定输出结构 |

你可以先把它理解成一句话：

> 最小可运行 RAG = 文档入库 + top-k 检索 + 带引用生成

## 3. 第一步不是写代码，而是定边界

最小可运行 RAG 的第一步，通常不是写数据库表，而是先回答：

> 这套系统到底要回答哪一类问题？

比如你可以只选下面一种：

- 内部制度问答
- 产品文档问答
- 项目知识问答
- 本地 Obsidian 笔记问答

一开始不建议做“全库都能答”。

因为范围一旦太大，就会同时遇到：

- 资料风格不一致
- 文档质量参差不齐
- 元数据缺失
- 权限模型复杂
- 评估样本很难定义

而窄场景的好处是：

- 你更容易判断答得对不对
- 更容易积累真实问题
- 更容易知道该优化哪一段链路

## 4. 第二步：保留结构，而不是只抽纯文本

RAG 最容易被低估的一层，就是解析。

很多人以为“只要把文字提出来就行”。但真正影响后续质量的，往往是你有没有保留住这些结构：

- 标题层级
- 段落边界
- 表格内容
- 列表项
- 来源文件
- 更新时间
- 原始路径

如果解析后只剩一整坨纯文本，后面会马上出现两个问题：

1. 检索虽然能召回一点东西，但不知道它原来属于哪一节。
2. 生成时能说出内容，却很难给出清楚引用。

所以一个更实用的原则是：

> 解析阶段要尽量保留结构，因为这些结构以后会变成 metadata、引用和过滤条件。

## 5. 第三步：chunk 不是越小越好

切分是 RAG 里最常见、也最容易掉坑的一层。

很多人第一次做，会本能地觉得：

> chunk 越小，检索越精细。

但太小会带来一个反效果：把上下文切没了。

比如原文是：

- 条件
- 例外
- 限制
- 金额

如果你把它切得太碎，模型可能只看到“金额”那一段，却没看到“仅限一线城市”或“特殊情况需要审批”这种前置条件。最后答案看起来像对的，但其实少了边界。

所以切分的目标不是小，而是：

- 每个 chunk 尽量自洽
- 关键条件不要被切断
- 长度别大到把噪音也一起带进来

刚开始时，一个足够实用的策略通常是：

- 按标题切大段
- 大段内部再按段落拼成中等大小 chunk
- 给一点重叠，避免边界信息断掉

## 6. 第四步：Embedding 和索引只是中间层，不是终点

当文档被切成 chunk 之后，下一步通常就是：

1. 用 embedding 模型把 chunk 变成向量。
2. 把向量和 metadata 一起写进可检索存储。

这一步当然重要，但最好不要把它神化。

embedding 做的是：

- 让语义相近的文本在空间里更靠近

它并不保证：

- 召回的一定就是答案
- 编号、术语、代号一定能找回来
- 用户口语表达一定能完美映射到文档写法

所以 embedding 和向量库，本质上只是“帮你把资料先找回来”的一层能力，不是 RAG 的全部。

## 7. 第五步：先别急着生成，先看 top-k

很多人一做完索引，立刻就去接模型生成答案。

但一个更稳的顺序是：

> 先检查检索结果本身，再接生成层。

也就是说，给定一个问题，你先只看：

- top-k 回来了什么
- 正确材料有没有进来
- 里面有没有明显噪音
- 来源信息够不够清楚

如果 top-k 里根本没有答案，那后面的生成再强也救不回来。

这也是为什么做最小可运行 RAG 时，最应该先确认的不是“模型说得顺不顺”，而是：

> 检索是不是至少把正确材料带进候选池了。

## 8. 第六步：生成阶段先固定输出格式

当 top-k 大致可靠后，才接生成层。

这时最容易犯的错误是，让模型自由回答。这样虽然看起来灵活，但后面很难评估，也很难做追溯。

所以最小版本里，最好先固定输出结构，比如：

1. 直接答案
2. 主要依据
3. 证据不足时的说明
4. 引用来源

这样做有几个好处：

- 回答更稳定
- 更容易肉眼检查
- 更容易后面做自动评测
- 更容易发现“模型是不是在胡补”

一个很关键的约束是：

> 如果检索材料不足，就允许模型明确说“不足以判断”。

这比让它顺着猜一个完整答案安全得多。

## 9. 这一篇的重点其实不是“搭得快”，而是“链路能看清”

最小可运行 RAG 的真正价值，不在于它简陋，而在于：

- 每一层都足够简单
- 每一层都能单独观察
- 每一层出错时都比较容易定位

你可以把它看成是一个观察窗。

有了这个观察窗，后面你再往里加：

- 查询改写
- 混合检索
- 重排
- 权限
- 评估集
- Agentic RAG

你才知道这些增强到底是在改善哪一段，而不是把系统越做越复杂，最后却说不清为什么有时候好、有时候坏。

## 10. 这篇先记住五个结论

1. 最小可运行 RAG 的目标不是做完所有能力，而是先形成一个可观察的闭环。
2. 第一步要先定边界，而不是一开始就把所有资料都塞进来。
3. 文档解析时保留结构，后面才能做好引用、过滤和追溯。
4. chunk 的目标不是越小越好，而是尽量保持语义完整。
5. 在接生成层之前，最值得先看的其实是 top-k 检索结果本身。
