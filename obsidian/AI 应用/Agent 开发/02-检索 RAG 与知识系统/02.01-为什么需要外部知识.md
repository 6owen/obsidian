# 为什么需要外部知识

> [!note]
> Part 01 解决的是“模型怎么开始行动”。这一篇开始解决另一个同样关键的问题：模型到底从哪里获得它回答任务所需的知识。

## 1. Part 02 在解决什么

在上一部分里，我们已经把链路走到了 Agent：

- 模型可以接收指令
- 可以调用工具
- 可以根据结果继续循环

但这还不够。

因为一个 Agent 就算“会做事”，也不代表它“知道该做什么”。很多任务真正难的地方，不是行动能力，而是知识来源。

比如这些问题：

- “帮我根据公司内部文档回答这个问题。”
- “读取我本地 Obsidian 里的笔记，再生成一份总结。”
- “查一下这个库最新官方文档的写法。”
- “结合我们项目代码和最近的报错日志，判断问题出在哪里。”

这些任务有一个共同点：

> 真正有用的知识，不一定在模型参数里，而是在外部世界里。

## 2. 只靠模型参数为什么不够

很多人第一次接触大模型，会默认觉得：

> 模型不是已经训练过海量数据了吗？那为什么还要检索？

问题就在于，模型参数里的知识虽然广，但并不天然满足真实任务的需求。

最常见的缺口有三类：

| 知识类型 | 例子 | 为什么参数知识不够 |
| --- | --- | --- |
| 通用但可能过时的知识 | 某个框架旧版本写法、过期产品信息 | 训练数据有时间边界，模型可能知道旧的，不知道新的 |
| 私有知识 | 你的笔记、公司文档、项目代码、数据库记录 | 这些内容根本没参与模型训练 |
| 当前实时知识 | 今天的网页内容、刚发生的报错、刚更新的配置 | 这些信息发生在调用时，而不是训练时 |

所以模型的参数知识更像是：

- 一个很大的背景知识库
- 一个通用推理底座
- 一个能理解材料、整理材料、生成回答的核心

但它不是你这次任务的完整知识来源。

## 3. 为什么不能直接把所有资料都塞进 prompt

看到这里，很多人会有一个很自然的想法：

> 既然模型不知道，那我把所有资料都粘进去不就行了？

这招在小规模场景里当然能用，但一旦材料变多，就会出现四个问题。

### 1. 上下文窗口不是无限的

模型一次能看的内容虽然越来越长，但依然有边界。

如果你的资料来自：

- 整个代码仓库
- 很多篇 Obsidian 笔记
- 大量 PDF、网页和日志

那你不可能每次都把所有东西完整塞进去。

### 2. 成本会快速升高

上下文越长：

- 请求越贵
- 返回越慢
- 缓存命中越难稳定

所以“每次全量硬塞”通常不是一个可持续方案。

### 3. 噪音会把真正重要的信息淹没

模型并不是看到越多就一定越聪明。

如果你把大量无关材料一起喂进去，真正关键的那几个片段反而更容易被稀释。结果就是：

- 回答变散
- 引用不准
- 重点抓错

### 4. 资料本身是会变化的

文档会更新，代码会改，笔记会新增，网页会失效。

如果你的系统没有“先找到当前版本材料，再喂给模型”的能力，那回答质量很快就会掉下来。

所以问题不是“能不能塞”，而是：

> 能不能每次只塞最相关、最新、最可信的那一小部分。

## 4. 知识进入模型，其实主要有四条路

理解 RAG 前，先把“知识怎么进模型”这件事想清楚。

一条回答里能用到的知识，大致来自四条路径：

| 路径 | 来源 | 优点 | 局限 |
| --- | --- | --- | --- |
| 参数知识 | 模型训练阶段学到的内容 | 广、默认可用 | 可能过时，不能覆盖私有资料 |
| 上下文知识 | 本次 messages 里显式喂进去的内容 | 准确、直接 | 窗口有限，成本高 |
| 检索知识 | 调用时从文件、网页、数据库里找回来的内容 | 新、可追溯、可更新 | 前提是先找得准 |
| 记忆知识 | 系统跨调用保存的偏好、历史选择、任务状态 | 有连续性 | 容易写错、污染或过期 |

可以先记一个很实用的判断：

```text
模型回答质量 = 参数知识 + 本次上下文 + 检索结果 + 合适的记忆
```

这里最重要的变化是：我们不再把“知识”只理解成模型训练时学到的东西，而是开始把外部知识动态接入到每次调用里。

## 5. RAG 到底在补什么

RAG 这个词很容易被讲得很神秘，但它最朴素的含义其实很简单：

```text
RAG = Retrieve + Augment + Generate
```

也就是：

1. 先检索：从外部资料里找相关内容。
2. 再增强：把相关片段连同来源、标题、Metadata 一起塞进当前上下文。
3. 再生成：让模型基于这些证据生成回答。

所以 RAG 的本质不是“用了向量数据库”，也不是“搞了一个很高级的 AI 组件”。

它的本质是：

> 不再把所有知识都预先塞进模型参数里，而是把外部知识在调用时按需取回，再注入到这次回答中。

如果用一句更直白的话说：

> RAG 其实就是“先找资料，再让模型看着资料回答”。

## 6. Context、Knowledge、Memory 不是一回事

这几个词在很多文章里经常混着说，但它们最好分开理解。

| 概念 | 它是什么 | 典型内容 | 核心问题 |
| --- | --- | --- | --- |
| Context | 这次调用里模型当前真的看到了什么 | messages、检索片段、工具结果 | 喂进去的内容够不够相关 |
| Knowledge Base | 系统外部可被检索的知识存量 | 文档、代码、笔记、网页、数据库 | 材料是否完整、可更新、可访问 |
| Memory | 系统保留下来的持续状态 | 用户偏好、任务进度、历史选择 | 什么该记、记多久、怎么避免污染 |

最容易混淆的地方在于：

- Knowledge Base 不等于 Context  
  因为知识库里的材料很多，但一次调用只会用到其中很小一部分。

- Memory 不等于 Knowledge Base  
  因为记忆更偏向“持续状态”，而不是完整资料库。

- Context 也不等于 Memory  
  因为上下文是这次真喂进去的，记忆只是潜在可被取回的一部分。

所以从系统视角看，通常是：

```text
Knowledge Base / Memory / 外部数据源
        ↓
      检索或读取
        ↓
      进入 Context
        ↓
      模型生成回答
```

## 7. 检索系统不等于知识系统

当我们说“做一个 RAG 系统”时，很容易把目标缩小成：

- 把文档切块
- 做向量化
- 查 Top-k
- 把结果拼给模型

这当然是基础能力，但它还不是完整知识系统。

一个真正可长期使用的知识系统，通常还要解决这些问题：

- 原始资料放在哪里
- 资料怎么更新和增量同步
- 资料有没有版本和来源
- 能不能回到原文核验
- 私有资料怎么做权限控制
- 结论能不能带引用、带证据、带时间性

所以：

> 检索系统主要解决“找”；知识系统还要解决“怎么存、怎么管、怎么追溯、怎么持续维护”。

这也是为什么这一部分不只讲 RAG，还要讲“知识系统”。

## 8. 这和 Agent 的关系是什么

到这里你会发现，RAG 和 Agent 其实不是互相替代的关系。

可以先这样理解：

- 没有 Agent，也可以有 RAG  
  比如一个普通问答系统：用户提问 → 系统检索 → 模型回答。

- 但有了 Agent，检索会变得更主动  
  Agent 可以自己决定：
  - 要不要搜
  - 去哪里搜
  - 一个问题要不要拆成多个子问题
  - 当前证据够不够
  - 要不要再搜一轮

于是系统就从“固定检索后回答”，逐渐演化成：

- Agentic Search
- Agentic RAG

也就是说，RAG 让模型有外部知识，Agent 则让模型能更主动地使用这些知识能力。

## 9. 这篇先记住五个结论

1. 模型参数里的知识很广，但不等于任务所需的最新、私有、实时知识。
2. 不能靠“每次把所有资料都塞进 prompt”来长期解决知识问题。
3. RAG 的本质是先检索相关材料，再把材料注入当前上下文后生成回答。
4. Context、Knowledge Base、Memory 是三个不同层次，不要混成一个词。
5. 检索系统解决“找”，知识系统还要解决结构、更新、权限、追溯和维护。
