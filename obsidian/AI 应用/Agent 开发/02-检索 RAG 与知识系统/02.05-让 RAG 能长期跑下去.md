# 让 RAG 能长期跑下去

![[assets/02-05-rag-ops-illustrations/01-rag-ops-hero.excalidraw]]

> [!note]
> 检索质量开始提升以后，你很快会撞上两个更现实的问题：第一，你怎么知道它真的变好了；第二，文档更新以后系统怎么跟着变。这一篇讲的不是“让 demo 更炫”，而是让 RAG 能长期跑下去。

## 1. “感觉好多了”为什么是最贵的一句话

RAG 优化最容易掉进的陷阱，就是靠感觉调参。

你可能会做这些事：

- 把 top-k 从 5 改成 8
- 把 chunk 变小一点
- 加一个改写 prompt
- 换一个 embedding 模型

然后问几道题，感觉回答顺了一些，于是就觉得系统变好了。

问题在于，这种“感觉”几乎不可复用：

- 你不知道到底是哪一步起了作用
- 你不知道是不是只对这几道题有效
- 你不知道这次优化会不会顺手弄坏别的问题

所以一套能长期跑的 RAG，必须尽早建立两个能力：

1. 评估：证明它到底有没有变好。
2. 更新：文档变了以后，系统能不能低成本跟上。

## 2. 评估集不是锦上添花，而是地基

最小评估集可以先很小，但最好尽快有。

它至少应该包含：

- 真实问题
- 对应的正确答案或答案范围
- 应该召回的关键 chunk 或来源

为什么这东西这么关键？

因为它会把“我觉得”变成“我知道”。

有了评估集以后，你每次改一项东西，都能回答：

- Recall 提高了吗？
- 噪音变少了吗？
- 最终答案更准了吗？

没有评估集时，所有优化都是盲调。

## 3. 最先看的通常不是答案，而是检索指标

评估 RAG 时，很多人会直接盯最终答案。

但一个更稳的顺序通常是：

1. 先看检索层
2. 再看生成层

因为如果检索根本没把正确材料带回来，那答案再差，也不是生成层一个人的锅。

所以最基础的几个指标通常是：

- Recall@k：该回来的材料有没有回来
- Precision@k：回来的候选里噪音多不多
- 最终答案准确率：模型有没有基于材料答对

这几个指标的关系可以粗暴理解成：

- Recall 太低：说明候选池里就没答案
- Precision 太低：说明候选池噪音太大
- 答案准确率低：说明要么材料不对，要么模型没用好材料

## 4. 评估真正解决的不是打分，而是防止退化

评估最大的价值，不只是给你一个分数，而是给你一个“防退化机制”。

你以后可能会持续修改：

- chunk 策略
- embedding 模型
- 检索参数
- prompt
- rerank 策略

如果没有评估集，每次修改都像拆盲盒。

而有了评估以后，哪怕它还不完美，至少你能知道：

- 这次改动是整体更好了
- 还是只在一小类问题上更好
- 以及有没有把以前答对的东西改坏

## 5. 第二个关键能力：别每次都全量重建

RAG 还有一个非常现实的问题：知识是会变的。

比如：

- 一篇产品文档被更新
- 一份制度文件换了版本
- 一份 FAQ 被补充了新问答

如果每次一改文档，你都要：

1. 重读全库
2. 重新切分所有文档
3. 重算全部 embedding
4. 重建整套索引

那系统很快就会变得昂贵而迟缓。

所以能长期跑的 RAG，通常都需要增量更新。

它的核心思想其实很简单：

> 只重算发生变化的那部分，而不是每次推倒重来。

## 6. 增量更新的本质：知道什么变了

增量更新要解决的问题不是“怎么重建”，而是：

> 怎么准确知道哪些文档真的变了。

最常见的做法通常是：

- 给文档保留来源标识
- 记录更新时间或版本号
- 或者直接给原始内容做 hash

这样下次同步时，就能区分：

- 没变：跳过
- 新增：入库
- 修改：只重算这份文档及其 chunk
- 删除：对应索引失效或删除

只要这层做好，更新成本就会一下子降很多。

## 7. 评估和更新，最好连成一个闭环

真正更稳的做法，不是把评估和更新拆开，而是把它们接成闭环：

1. 文档同步
2. 增量更新索引
3. 自动跑评估集
4. 看指标有没有明显下降

这样系统每次变更后，你都能更快知道：

- 是不是知识更新带来了新问题
- 是不是某次优化把召回打坏了
- 是不是某类问题开始持续退化

换句话说，一个长期可用的 RAG，不只是会回答，还要会体检。

## 8. 这篇真正想讲的是：RAG 不是一次性工程

做到这里，Part 02 的思路会越来越清楚：

- RAG 不是搭一次就结束
- 它是一个持续变化的系统

文档会变：

- 资料会更新
- 用户问题会变化
- 术语会演进
- 权限会调整

所以真正可用的 RAG，一定要从一开始就接受这个事实：

> 你不是在做一个静态 demo，而是在做一个会持续变化的知识系统。

## 9. 这篇先记住五个结论

1. “感觉变好了”不是评估，最多只是灵感来源。
2. 评估集的价值，不只是打分，更是防止系统悄悄退化。
3. 先看检索层指标，再看生成层表现，定位会更清楚。
4. 能长期跑的 RAG 一定要支持增量更新，而不是每次全量重建。
5. 更新和评估最好接成闭环，让系统每次变化后都能自检。

## 10. 下一步

当系统开始能长期跑，另一个更敏感的问题就会立刻出现：[[02.06-权限、安全与可追溯]]。

因为一个能检索、会回答、还能不断更新的系统，如果权限边界错了，后果通常不是“不准”，而是“泄露”。
