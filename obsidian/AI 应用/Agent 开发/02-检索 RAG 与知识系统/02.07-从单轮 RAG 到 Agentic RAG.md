# 从单轮 RAG 到 Agentic RAG

![[assets/02-07-agentic-rag-illustrations/01-agentic-rag-hero.excalidraw]]

> [!note]
> 到前面为止，我们讲的 RAG 基本还是“检索一次，再回答一次”。这对很多事实型问题已经足够，但一旦问题开始变成对比、归因、多来源综合，单轮 RAG 就会开始吃力。这也是 Agentic RAG 出现的位置。

## 1. 单轮 RAG 什么时候开始不够

单轮 RAG 的典型流程是：

1. 用户提问
2. 检索一次
3. 把结果喂给模型
4. 模型生成答案

这条链路在事实查询里往往没有问题，比如：

- “公司的报销标准是什么？”
- “某个接口鉴权怎么写？”
- “某份制度最后更新时间是什么？”

但一旦问题开始变复杂，单轮 RAG 就会暴露边界。

比如：

- “对比 Q2 和 Q3 的毛利率，哪个变化更大？”
- “最近三个月销售额下降，主要原因是什么？”
- “这份合同里有没有对我们不利的条款？”

这些问题有一个共同点：

- 需要拆成多个子问题
- 需要多次检索
- 可能还要做计算、比较或判断

也就是说，它们不是“拿到一组材料就能答”，而是“边找边想，边想边补材料”。

## 2. Agentic RAG 不是换了一个新模型

Agentic RAG 最容易被误解的地方，就是听起来像一套全新技术。

但如果说得更朴素一点，它其实只是：

> 把检索当成模型可调用的一种工具，再把这件事放进 Agent Loop 里。

也就是说，模型拿到问题以后，不是只能被动等你把材料喂给它，而是可以主动参与这些决策：

- 要不要先检索
- 先查哪个方向
- 这次证据够不够
- 要不要继续补查
- 是否要调用别的工具

所以 Agentic RAG 增加的，不是“更神秘的知识能力”，而是“检索决策层”。

## 3. 它真正解决的，是多步信息不足问题

单轮 RAG 最大的问题不是“检索不出来”，而是：

> 复杂问题往往不是一次检索就能把证据凑齐。

比如“对比 Q2 和 Q3 毛利率变化”的问题，系统至少可能要做这些事：

1. 找 Q2 毛利率
2. 找 Q3 毛利率
3. 比较差值
4. 再找造成变化的原因

这已经不是一个 query 能解决的了。

如果你强行把整个问题直接交给单轮检索，它常常会发生两种事：

- 要么检索太散，什么都沾一点
- 要么模型直接硬补出一个看起来完整的答案

而 Agentic RAG 的价值，就在于它允许系统承认：

> 我现在证据不够，所以我要再查一次。

## 4. 这时检索就从“流水线环节”变成了“工具”

一旦进入 Agentic RAG，检索的角色就变了。

在基础 RAG 里，检索是固定环节：

- 问题一来，就查一次

在 Agentic RAG 里，检索更像工具：

- 模型根据当前状态决定何时查、查什么、查几次

这带来一个很重要的变化：

- 检索不再只是系统内部的一段固定逻辑
- 它变成模型可以调度的能力

而一旦它变成工具，前面讲过的那些问题就全部还得继续成立：

- 权限不能丢
- metadata 不能丢
- 噪音控制不能丢
- 引用和来源不能丢

也就是说，Agentic RAG 不是跳过前面的基础能力，而是建立在前面那套基础上。

## 5. 所以 Agentic RAG 的难点不是 while 循环，而是边界控制

很多人第一次看到 Agentic RAG，会觉得核心难点是“多步推理”。

但从工程角度看，真正难的通常不是循环本身，而是控制它别跑野。

因为一旦把决策权交给模型，就会出现这些新风险：

- 重复查同一个问题
- 在无效方向上一直补查
- 为了补证据一直烧 token
- 工具太自由，行为不可预测

所以一个更可用的 Agentic RAG，一定要带边界：

- 最大步数
- 查询去重
- 成本上限
- 工具集合限制
- 停止条件

换句话说，Agentic RAG 的真正形态不是“让模型自由乱搜”，而是：

> 在明确边界内，让模型拥有有限但实用的检索决策权。

## 6. 什么时候该上，什么时候其实别上

这是特别重要、但经常被省略的一点。

Agentic RAG 不是默认更高级的替代品，它有明显代价：

- 更慢
- 更贵
- 更难调试
- 更难评估

所以它更适合：

- 对比类问题
- 归因类问题
- 多来源综合问题
- 需要多跳补证据的问题
- 需要调用额外工具的问题

但它不适合所有问题都默认走一遍。

像下面这些问题，单轮 RAG 通常就够了：

- “公司地址是什么？”
- “报销标准在哪份文档里？”
- “某个接口参数怎么写？”

如果这种问题也走 Agentic RAG，系统只会变慢，不会更值。

## 7. 更实际的做法：路由，而不是一刀切

所以更好的工程策略通常不是“全量 Agentic”，而是：

1. 先判断问题复杂度
2. 简单问题走单轮 RAG
3. 复杂问题再切到 Agentic RAG

这也是为什么 Agentic RAG 更像一个升级层，而不是基础层。

你可以把它理解成：

- 基础 RAG：常规查询的默认通道
- Agentic RAG：复杂问题的增强通道

## 8. 这篇先记住五个结论

1. 单轮 RAG 在事实查询上很好用，但在多步、多来源综合问题上会开始吃力。
2. Agentic RAG 不是新模型，而是把检索能力接进 Agent Loop。
3. 它真正增加的是“检索决策层”，也就是模型能决定何时搜、搜什么、要不要补查。
4. Agentic RAG 仍然建立在前面的检索、权限、评估底座之上，不是跳过它们。
5. 它不该默认用于所有问题，更合理的做法通常是按复杂度路由。
