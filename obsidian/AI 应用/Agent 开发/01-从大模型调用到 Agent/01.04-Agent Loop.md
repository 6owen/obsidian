# Agent Loop

> [!note]
> Tool Calling 让模型能提出“我要调用工具”。Agent Loop 则让整个系统能接住结果、继续思考、继续执行，直到任务完成或被系统主动停止。

## 1. 为什么只有 Tool Calling 还不够

![[assets/01-04-agent-loop-illustrations/01-loop-wheel.svg]]

假设模型先调用了搜索工具，拿到搜索结果以后，会发生什么？

如果系统没有 loop，流程通常就卡在这里：

- 模型发出工具调用意图
- 程序执行工具
- 得到结果
- 然后就停住

但真实任务往往不是一步完成的，而是：

1. 先查一下。
2. 再根据结果决定要不要继续查。
3. 或者改成读文件。
4. 或者已经证据足够，可以给答案。

这就是 Agent Loop 的必要性：它把“调用一次工具”扩展成“围绕目标持续决策”。

## 2. Agent Loop 的最小闭环是什么

一个最小闭环通常是：

1. 给模型当前上下文。
2. 模型决定：直接回答，还是调用工具。
3. 如果调用工具，程序执行工具。
4. 把工具结果喂回模型。
5. 模型继续判断下一步。
6. 重复这个过程，直到完成或触发停止条件。

所以 Agent Loop 其实就是一句话：

> 观察 -> 决策 -> 执行 -> 回传 -> 再决策

## 3. 最小伪代码

最小版本大概会长这样：

\`\`\`js
async function runAgent(messages, tools) {
  for (let step = 0; step < 8; step++) {
    const response = await callModel({ messages, tools })
    const message = response.choices[0].message

    messages.push(message)

    if (!message.tool_calls || message.tool_calls.length === 0) {
      return message.content
    }

    for (const toolCall of message.tool_calls) {
      const result = await executeTool(toolCall)

      messages.push({
        role: "tool",
        tool_call_id: toolCall.id,
        content: JSON.stringify(result),
      })
    }
  }

  throw new Error("Step limit reached")
}
\`\`\`

这段代码并不复杂。复杂的从来不是 loop 这个壳子，而是：

- 你让模型看什么
- 你有哪些工具
- 工具结果怎么组织
- 什么时候该停

## 4. 停止条件为什么这么重要

没有停止条件的 loop，几乎一定会出问题。

一个靠谱的 Agent Loop，通常至少要有这些停止条件：

- step limit：最多走多少轮
- success condition：什么时候算任务完成
- timeout：整个任务最多跑多久
- budget：最多允许消耗多少 token、多少钱、多少次工具调用

## 5. 往回喂什么，不是越多越好

很多人第一次写 loop，会陷入一个误区：

> 工具执行完以后，把所有东西一股脑塞回去。

这样当然有时能跑，但很快会遇到几个问题：

- 上下文越来越长
- 成本越来越高
- 缓存命中率变差
- 关键信息被噪音淹没

更好的做法是：

- 回传真正有用的工具结果
- 必要时做摘要或结构化整理
- 把错误也清楚回传给模型

## 6. 常见失败模式

- 死循环
- 早停
- 工具漂移
- 上下文膨胀

loop 不是“无限继续”，而是“可控地继续”。

## 7. 这篇先记住什么

1. Tool Calling 解决的是“模型怎样表达动作意图”。
2. Agent Loop 解决的是“工具结果回来以后，系统怎样继续走下去”。
3. 一个靠谱 loop 至少要有步数限制、超时、预算和完成条件。
4. loop 的难点不是写一个 \`for\`，而是控制上下文、工具和停止逻辑。
