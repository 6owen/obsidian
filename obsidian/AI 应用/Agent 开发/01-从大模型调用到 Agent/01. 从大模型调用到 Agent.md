# 从大模型调用到 Agent

这一部分想解决的问题很简单：我们明明已经能用一条 API 调用大模型，为什么还会继续发展出 Agent 这种更复杂的系统？

先不急着下定义。下面这个故事里没有计算机，只有一面会回答问题、却永远记不住昨天的镜子。

## 寓言：无记之镜与最后一格铜漏

### 一、铜漏只剩七格

临川城的雨下到第九日，江水越过了旧堤上的第三道刻线。

巡水司的铜漏只剩七格。天亮以前，若不能把洪峰引入西面的旧河道，北城墙就会从最薄的一段裂开。城里有三万人，城外还有四座来不及迁走的村庄。

沈砚带着巡水司的铜牌进入问策室。铜牌只能打开这一间屋子的门，也只允许他使用屋里那面黑镜。镜子不看人，镜面上永远只有一句话：

> 请递上本次卷宗。

这面镜子读过王朝两百年的河工典籍、奏疏与灾情记录。只要把文字写在纸上推入镜座，它就会在镜面上续出回答。沈砚十九岁解出过三郡都没算明白的分洪题，因此相信，真正聪明的人不需要搬来整座档案库，只需要问对那一句话。

### 二、一句漂亮的问题

沈砚写下：

> 今夜应开哪一道闸，才能保住临川城？

纸刚没入镜座，镜面便浮出两个字：

> 七闸。

“看，”沈砚把纸交给都水使邵衡，“问题越干净，答案越干净。”

邵衡没有反对。他负责的是城墙，不是镜子。若关闭所有外闸，北城至少还能多撑两个时辰；代价只是洪水会转向城外四村。在没有更可靠方案时，他宁可保住更多人。

开闸令发出不到一刻，东仓的铜铃却先响了。

七闸去年修过，闸底加了一道从未画进旧图的斜槛。闸门只抬起半尺，水流便被斜槛推向东渠。三百石粮食泡进泥水，北城水位却只降了半寸。

沈砚得到了一句完整、流畅而且错误的回答。

### 三、镜子忘了“刚才”

掌档吏阿绫捡起地上的问策纸，在背面写道：

> 你刚才为什么选择七闸？

镜面沉默片刻，浮出一行字：

> “刚才”指什么？卷宗中没有此前的问答。

沈砚抬头看它，像第一次真正看见这面镜子。

阿绫把三样东西摊在桌上：去年的旧河图、七闸修缮簿、半个时辰前送来的水位牌。镜子读过无数河工文章，却没有走出过问策室。它不知道今夜正在下雨，不知道闸底多了斜槛，也不知道自己上一刻说过什么。

“它没有忘，”阿绫说，“是我们根本没把这些事告诉它。”

沈砚不愿承认自己不知道答案。但东仓的水已经漫到第二级台阶，铜漏又空了一格。

### 四、越来越厚的卷宗

他们重新装订了一册《临川问策卷》。

第一页不是问题，而是三条不能违背的规矩：

1. 首要目标是降低北城水位，同时避免把未经评估的洪峰转向村庄。
2. 证据不足时，不得假装已经知道。
3. 可以申请查档和测量；涉及开闸、撤防和改道，必须由都水使验印。

后面依次放入今夜的目标、刚才的问答、七闸失败的结果、最新水位、修缮簿，以及一份只讲如何判断回流和淤积的《河工验水诀》。

沈砚最后才写上新的问题：

> 下一步应当做什么？

这一次，镜面没有急着给出闸号，而是浮出一张格式严整的纸条：

> 请求一：测量西堤三处水位，返回刻线、时间与测量人。
>
> 请求二：查找三闸最近一次维修记录，返回新增构件与通水试验结果。

阿绫把纸条撕下来，却没有动。

“它已经说了要查什么。”沈砚催道。

“说要查，不等于已经查过。”阿绫把纸条递给两名巡水卒，“镜子没有腿，也没有档案库的钥匙。”

### 五、镜子无手，回信有泥

一名巡水卒赶往西堤，另一名去库房调三闸卷宗。半个时辰后，两人带回盖章的回信。西堤水牌沾着泥，三闸卷宗缺了最后一页。

阿绫把结果续进《问策卷》，连同“缺页”这件事一起递回镜座。

镜子读完后，又提出请求：

> 三闸资料不足。请读取城南水车行的夜间流速记录，并核验记录时间是否与本城铜漏一致。

水车行不归巡水司管。过去若要取数，须先找行会、再找驿站，往返至少一个时辰。幸好两年前各司共同订过一册《百工通契》：每一种可借用的器具和档案，都有固定名称、用途、参数、回信格式和权限印记。

阿绫照契书填写请求，驿站按统一格式把水车行的记录送了回来。镜子不需要认识水车行掌柜，也不需要学会骑马；它只需要看懂契书中声明的能力，以及送回来的结果。

新的记录表明，城南铜漏比巡水司慢了一刻。若忽略这点，两组流速会被当成同时发生，结论将恰好相反。

沈砚第一次主动在卷宗里写下：

> 前一判断所需证据不足。继续核验，不得开闸。

### 六、卷宗不能无限生长

铜漏还剩四格，《临川问策卷》却已经厚得合不上。

每多放一张纸，镜子读卷的时间就更长。更糟的是，旧回信、重复水位和无关修缮记录混在一起，真正重要的变化反而沉到了纸堆底下。

阿绫拆开卷宗，把不变的部分放在前面：三条规矩、《河工验水诀》、可用器具清单和已经确认的旧记录。变化的水位、最新回信和当前问题统一追加在末尾。过长的原始记录只保留摘要，原件仍留在桌边，必要时再查。

问策室的老书吏又取来一块蜡版。镜座会在一炷香内保留相同卷首的压痕；下一次若卷首内容和次序完全不变，就不必从头描摹。若在第一页塞进新的时刻或随手调换纸张，压痕便不能复用。

蜡版只省去了重复描摹卷首的工夫。最新水位仍要读，新的问题仍要判断，最后的回答也仍要重新写。

他们因此抢回了半格铜漏。

### 七、红印与最后一页

第五次问策后，镜子给出了一套动作：

> 先试开三闸一尺，观察西堤三处水位；若两处下降且回流未超过红线，再开五闸半尺。否则立即复位。

邵衡却按住了官印。

“试开也是开。”他说，“若水车行记录仍有错，四村会先被冲掉。关闭所有外闸，至少能确保城中大多数人活着。”

他的选择冷酷，却不荒谬。所有工具都可能返回错误，卷宗也可能遗漏关键事实。镜子给出的只是一项依据现有材料推导出的行动方案，不是一道免于负责的天命。

此时，城西最后一座望楼送来残破的风旗记录。还缺半页，恰好缺了洪峰转向的时刻。

沈砚可以假装证据已经足够，以保住自己“少年神算”的名声；也可以承认不知道，把最后一次查证机会花在一个尚未证明有用的方向上。

他把开闸令推回邵衡面前。

“先不盖印。”沈砚说，“请镜子告诉我们，缺失的那半页会影响哪一个判断；再只查那个判断。”

这是他今夜第一次没有向镜子索要答案，而是要求它指出自己的未知。

### 八、第六次潮声

镜子请求读取北塔的风铃停摆记录。风铃不是水利器具，却能确定狂风转向的准确时刻。《百工通契》中恰好登记了它，权限也只需读取，不需要动用任何机关。

回信补上了最后一个时间点。三闸的试开方案仍然成立，但安全窗口只有一刻，且必须每半刻重新测量一次。

邵衡终于盖下红印。

巡水卒试开三闸一尺，阿绫记录结果，把新水位续回卷宗。镜子判断回流低于红线，请求开五闸半尺。邵衡再次验印，闸卒执行；新结果又回到镜前。

观察，判断，申请，验印，执行，回传。

同一条路走了六次。每一次都没有换镜子，只是卷宗里多了真实世界刚刚给出的结果。

第六次潮声响起时，北城水位终于退回第二道刻线。卷宗首页写明的完成条件已经满足。沈砚没有再问“还能不能更好”，而是命人封卷、停闸。

铜漏还剩最后一格。

### 九、真正会办事的东西

天亮后，邵衡站在满地泥水里问：“昨夜那面镜子，后来为什么忽然变聪明了？”

沈砚看向问策室。镜子仍旧漆黑。若现在只递进去一句“刚才发生了什么”，它依然答不出来。

“它没有变聪明，也没有记住我们。”他说，“变的是镜子外面。”

他们给镜子准备规则和目标，把旧问答与新证据装进卷宗；允许它用统一格式提出请求，让真正持有钥匙、仪器和双手的人去执行；再把结果送回来，让同一面镜子继续判断。同时，他们用官印限制权限，用铜漏限制时间和轮次，用红线规定何时成功、何时必须停止。

镜子负责给出下一段最合适的文字。真正把文字变成行动的，是卷宗、档案、信使、器具、契约、官印和一次次回传共同组成的系统。

许多年后，西堤碑记没有把它称作“神镜”。碑上只刻了两个异邦词：

> Model 是镜。
>
> Agent 是镜子外面那套会继续做事的系统。

## 故事之后：它真正讲的是什么

这个故事讲的是从一次大模型调用，到 Chat，再到 Agent 的连续演化。

核心命题只有一句：

> Agent 不是一个突然变得更聪明的新模型，而是围绕同一个模型增加上下文、工具、状态、循环、权限和停止条件后形成的执行系统。

### 1. 故事元素与技术概念的映射

| 故事中的事物 | 真正对应的概念 |
| --- | --- |
| 问策镜 | 大模型（LLM），根据本次输入生成最可能、最合适的后续内容 |
| 进入问策室的门与铜牌 | Endpoint 与 API Key：请求送到哪里，以及调用者是否有权限 |
| 选择哪一面镜子 | Model 参数：本次具体调用哪个模型 |
| 最初的一句话 | 最小 Prompt，也就是最简单的一次模型调用 |
| 《临川问策卷》 | 本次请求的 Context / Messages |
| 卷首三条规矩 | System Instructions / System Prompt |
| 旧问答与历次回信 | History Messages、Tool Results 与任务状态 |
| 《河工验水诀》 | Skill：给模型补充做事方法、领域规则与行为规范 |
| 器具清单和格式严整的请求 | Tool Schema 与 Tool Calling |
| 巡水卒、档案吏和真实器具 | 真正的工具执行层 |
| 《百工通契》 | MCP 一类标准化连接协议，用统一方式暴露外部工具和资源 |
| 反复“观察—判断—执行—回传” | Agent Loop |
| 官印、铜漏、红线 | Guardrails：权限、预算、步数、超时和完成条件 |
| 短时保留卷首压痕的蜡版 | Prompt Cache / Prefix Cache |
| 镜子外面的完整系统 | Agent |

### 2. 一次调用、Chat 和 Agent，本质上调用的仍是同一个模型

最简单的调用只需要：

> 用户问题 → 模型 → 回答

在工程上，这完全可以只是一条 curl 或 HTTP 请求：Endpoint 指定请求送到哪里，API Key 负责鉴权，Model 指定使用哪个模型，Messages 则装着这次真正交给模型的上下文。

Chat 没有改变模型的基本工作方式，只是把输入组织成一组有角色和顺序的消息，例如：

- system：系统规则和身份
- user：用户问题
- assistant：模型以前的回复
- tool：工具执行结果

Temperature、max_tokens、stream 等参数可以继续控制输出的发散程度、最大长度和返回方式，但它们不会自动为模型增加记忆、工具或执行能力。

到了 Agent，底层仍然是在发送模型请求。区别是每次请求里可能还会拼入：

- 历史消息与当前任务状态
- 检索到的文档、代码或网页
- Skills 提供的方法和规则
- Tools 的名称、描述与参数结构
- MCP 暴露的工具和资源说明
- 前几轮工具调用的结果
- 用户这一次的新问题

因此，Agent 并不是把一次调用替换成另一种神秘计算，而是让外层程序不断准备更合适的输入，并接住模型输出继续工作。

### 3. 模型本身无状态，状态保存在应用外层

镜子无法理解“刚才”，对应的是模型通常不会在一次请求结束后自动保存会话。

Chat 看起来能够记住前文，是因为应用把之前的消息保存下来，并在下一次请求时重新发送。Agent 看起来能够记住任务进度，也是因为外部系统保存了：

- 历史对话
- 工具调用与返回结果
- 已经完成的步骤
- 中间文件和工作区状态
- 用户偏好或长期记忆

所以更准确的表达是：

> 无状态模型 + 外部状态保存 + 每轮重新注入 = 看起来有状态的 AI 应用

模型看到的内容越完整，它越可能作出符合当前局势的判断；但上下文更多不等于事实一定正确。错误、过期或互相矛盾的材料，同样会把模型带向错误答案。

### 4. Tool Calling 只是动作意图，不是动作本身

镜子写出“去测水位”，并不表示水位已经测完。这对应 Tool Calling 的职责边界：

1. 模型根据上下文判断是否需要工具。
2. 模型输出工具名称和参数。
3. 外部程序验证参数、权限与风险。
4. 程序真正执行搜索、读取文件、访问接口或写入数据。
5. 程序把结果作为新的消息回传模型。

模型负责提出下一步，程序负责真实执行。把这两者混为一谈，会让权限、错误处理和安全边界全部失控。

Tools、Skills 和 MCP 也不是让模型“凭空获得新智能”：

- **Tool** 提供可以执行的能力。
- **Skill** 提供做事的方法、规则或领域知识。
- **MCP** 提供连接与描述外部工具、资源的标准方式。

它们最终都会以工具定义、文字说明或执行结果的形式进入模型上下文。

### 5. Agent Loop 让一次建议变成可持续执行

单次 Chat 通常到回答为止。Agent Loop 则把一次调用放进闭环：

> 观察当前上下文 → 模型决策 → 调用或执行工具 → 回传结果 → 再次决策

这个循环不能无限运行。至少应该明确：

- 最大步数
- 总超时时间
- Token、费用或工具调用预算
- 成功条件
- 高风险操作的授权方式
- 工具失败、参数错误和证据不足时如何退出

故事中第六轮水位达标后立即封卷，就是成功条件触发后的正常停止。如果没有停止条件，一个 Agent 可能死循环、不断消耗预算，也可能在任务已经完成后继续制造风险。

### 6. 上下文不是越多越好

不断把所有原文、日志和工具结果塞回模型，会造成上下文膨胀：

- 请求更慢、费用更高
- 关键信息被噪声淹没
- 重复内容增加
- 缓存更难命中
- 更容易超过上下文窗口

因此，真实系统通常需要区分：

- 稳定不变的系统规则和工具定义
- 需要长期保存的任务状态
- 本轮真正相关的检索材料
- 可以摘要的旧工具结果
- 必须保留原文以便核验的证据

这不是简单地“喂得越厚越好”，而是要让上下文完整、相关、可追溯，并控制噪声。

### 7. 缓存复用的是重复前缀，不是最终答案

故事里的蜡版对应 Prompt Cache 或 Prefix Cache。

当多次请求的前半部分保持相同，例如 system prompt、tools schema、skills 说明和稳定的历史前缀，模型服务可能复用这部分已经计算过的处理结果。因此首字延迟和费用可能下降。

但缓存通常不意味着“这次不用思考，直接拿出上次回答”。新的用户问题、最新工具结果和最终输出仍然需要计算。缓存还通常具有有效期，并且对内容、顺序和格式敏感。把时间戳、随机 ID 等动态字段放进稳定前缀，也可能破坏命中。

### 8. 什么时候才真的需要 Agent

如果任务只是解释概念、改写文本或生成一份草稿，单次调用或 Chat 往往已经足够。

当任务同时具备下面几项特征时，Agent 才开始有价值：

- 必须读取外部资料或最新信息
- 必须操作文件、接口或其他真实系统
- 下一步取决于前一步结果
- 需要多轮纠错和验证
- 需要持续保存任务状态
- 需要明确的权限、预算与停止规则

第一个 Agent 不应该从“万能助手”开始。更稳妥的实施方式是：

1. 选择一个窄任务。
2. 只提供一个或少量工具。
3. 写清工具名称、描述和参数约束。
4. 设置最大步数、超时与成功条件。
5. 记录每轮输入、工具调用、结果和停止原因。
6. 用可验证任务测试完成率、工具选择准确率、耗时和成本。

这时可以把全文压缩成一个公式：

> Agent = Model + Instructions + Tools + State + Loop + Guardrails

模型仍然是负责理解和生成的核心，但真正让它从“会回答”走向“能围绕目标持续行动”的，是模型外面的工程系统。
