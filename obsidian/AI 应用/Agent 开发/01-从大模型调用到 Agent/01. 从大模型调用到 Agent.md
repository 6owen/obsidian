# 从大模型调用到 Agent

这一部分想解决的问题很简单：我们明明已经能用一条 API 调用大模型，为什么还会继续发展出 Agent 这种更复杂的系统？

先不急着下定义。下面的故事从一个“什么都知道”的神秘装置开始，看它怎样一步一步从只会回答，变成能够持续完成任务的“百事通”。

## 寓言：从天而降的“百事通”

### 一、落进院子的黑匣子

青石镇坐落在山谷里。镇外地势低，每到雨季，都要靠东边的排水泵站把积水送进河道。

阿木是镇上的维修师，负责机器和线路。小禾负责保管图纸、维修手册和每一次故障记录。他们共同守着山脚下的一间修理铺。

一个没有雷声的夜晚，一道白光掠过屋顶。一个巴掌大的黑匣子落进修理铺的院子，外壳没有裂痕，正面只有一块发亮的屏幕：

> 请输入问题。

阿木试着问它为什么会下雨、齿轮为什么会磨损、怎样判断电机过热。黑匣子每次都能迅速给出完整答案，有些内容连维修手册里都没有。

“以后就叫你百事通。”阿木说。

### 二、泵站停了

几天后，天气站发来暴雨预警。三个小时后，大雨将进入山谷。

偏偏这时，东边的排水泵停止出水。

阿木赶到泵站，先做了常规检查：供电正常，电机能够启动，但传动带有些松，边缘也出现了磨损。过去遇到类似情况，问题通常出在传动带上。

他把观察结果写给百事通：

> 排水泵能够启动，但出水很小。传动带松动，边缘有磨损。现在应该先检查哪里？

百事通回答：

> 先断电，重新张紧或更换传动带。传动带打滑会使水泵转速不足，是出水量下降的常见原因。

这个判断并不荒唐，也和阿木的初步判断一致。

阿木断开电源，更换传动带，再重新启动。水流却没有恢复，电机电流反而开始上升。他立即停机，避免电机烧毁。

维修方案没有造成事故，却浪费了半个小时。乌云已经越过山口。

### 三、它知道很多，却不知道“这里”

阿木回到修理铺，问百事通：

> 你刚才的方法为什么没有解决问题？

百事通回答：

> 当前信息中没有“刚才的方法”和执行结果，无法判断失败原因。

阿木把前一次回答重新递给它。百事通这才开始分析，但仍然只能列出几种可能：进水口堵塞、叶轮卡住、阀门故障，或者压力数据异常。

小禾看出了问题。

“它知道书里写过什么，却不知道泵站现在是什么样。”她说，“它看不到压力表，听不到电机的声音，也不会自动记住上一轮发生过什么。”

百事通不是故意给错答案。它只是根据阿木提供的有限信息，给出了最可能的判断。

### 四、先给它一份完整任务

小禾在修理铺的旧电脑里建立了一份任务记录。

记录的第一页是目标：

> 在暴雨到达前恢复排水，并让出水量连续十分钟高于安全线。

第二页是规则：

1. 涉及拆机时必须先断电。
2. 证据不足时先检查，不得直接猜测。
3. 高风险操作需要阿木确认。
4. 最多执行六轮；达到安全线后立即停止。

后面依次放入阿木的现场观察、百事通的第一次建议、更换传动带后的结果、排水泵维修手册，以及泵站里可以使用的仪表和工具。

小禾写了一个简单程序。以后每次向百事通提问，程序都会把这些内容连同最新问题一起发送。

百事通仍然是原来那个百事通，但它每一次都能重新看到任务目标、以前发生的事和当前进度。

这一次，百事通没有直接给维修结论，而是提出了三个检查请求：

> 1. 读取进水口与出水口的压力。
> 2. 读取电机电流。
> 3. 拍摄过滤网正面的照片。

### 五、给百事通装上“眼睛和手”

阿木和小禾把压力传感器、电流表、摄像头、手册查询和工具房库存接入旧电脑。

每一种能力都有明确的名称、用途、输入参数和返回格式。百事通可以按照同一种格式提出请求，电脑负责检查权限，再调用对应的仪表或程序。

百事通请求读取压力，不等于压力已经被读取；百事通请求拆开过滤网，也不等于过滤网已经被拆开。

传感器负责观察，程序负责传递数据，阿木负责断电、拆机和真正的维修。

第一轮检查结果很快返回：

- 过滤网前后的压差异常
- 电机电流偏高
- 摄像头里能看到树叶和泥沙覆盖在过滤网上

百事通根据这些结果提出下一步：

> 断电并清理过滤网，然后重新读取压力和电流。

阿木确认操作，清理过滤网。水泵恢复了出水，但压力仍然周期性波动。

### 六、一次不够，就再来一次

新的压力和电流被写回任务记录，再次发送给百事通。

百事通根据变化后的结果请求检查止回阀。阿木断电拆开阀盖，发现一块碎石卡在阀片下方。碎石让水流不断回冲，也让传动带看起来像是在打滑。

阿木取出碎石，装回阀盖，再次启动水泵。

压力稳定了，电机电流回到正常范围，出水量连续十分钟高于安全线。程序判断任务已经完成，不再继续调用百事通，也不再执行新的工具请求。

整个维修过程其实一直在重复同一条链路：

> 观察现场 → 百事通判断 → 请求工具 → 执行操作 → 返回结果 → 再次判断

为了减少重复处理，小禾把始终不变的任务规则、维修手册和工具说明固定在记录前面，只把最新数据追加在末尾。短时间内，百事通可以复用相同的前半部分；新的检查结果和新的回答仍然需要重新处理。

暴雨落进山谷时，泵站已经恢复排水。

### 七、同一个百事通

阿木松了一口气：“它终于学会维修这台水泵了。”

小禾断开传感器，删除任务记录，只把最初的问题重新发给黑匣子。

百事通仍然建议先检查传动带。

它没有在维修过程中变成另一个更聪明的东西。改变的是它外面的系统：

- 任务记录让它每轮都能看到历史和当前状态。
- 维修手册补充了完成任务所需的方法。
- 传感器和摄像头给了它观察现场的能力。
- 工具和阿木让它的请求可以变成真实操作。
- 循环让它能够根据结果修正下一步。
- 权限、轮次和完成条件阻止它无限行动。

从那天起，“百事通”不再只指那个从天而降的黑匣子，而是指修理铺里这整套能够持续完成任务的系统。

黑匣子本身只是 Model。

围绕它建立的记录、工具、状态、循环和边界，共同组成了 Agent。

### 八、下一扇门

第二天，镇上送来一台刚上市的新型控制器。百事通给出的维修方法来自旧型号，和眼前的机器对不上。

小禾找到了厂家昨天才发布的维修公告。

百事通没有读过它，也不可能凭空知道它。

阿木看着修理铺里一排排没有整理的图纸和手册，问：“我们已经给了它眼睛和手，接下来还缺什么？”

小禾腾空一个书架，把新的维修公告放了进去。

“还缺一套它能够随时查找、能够知道来源、也能够不断更新的知识系统。”

百事通的第一次改造完成了。它的第二次改造，将从这个书架开始。

## 故事之后：它真正讲的是什么

这个故事讲的是从一次大模型调用，到 Chat，再到 Agent 的连续演化。

核心命题只有一句：

> Agent 不是一个突然变得更聪明的新模型，而是围绕同一个模型增加上下文、工具、状态、循环、权限和停止条件后形成的执行系统。

### 1. 故事元素与技术概念的映射

| 故事中的事物 | 真正对应的概念 |
| --- | --- |
| 从天而降的黑匣子 | 大模型（LLM），根据本次输入生成最可能、最合适的后续内容 |
| 阿木最初单独提出的问题 | 最小 Prompt，也就是最简单的一次模型调用 |
| 任务记录和自动拼装程序 | Chat Messages、Context，以及应用保存的任务状态 |
| 任务目标与四条维修规则 | System Instructions / System Prompt |
| 以前的建议、操作和测量结果 | History Messages 与 Tool Results |
| 排水泵维修手册 | Skill 与完成任务所需的领域知识 |
| 仪表的名称、参数和返回格式 | Tool Schema |
| 旧电脑提供的统一连接方式 | MCP 一类用于暴露外部工具和资源的协议 |
| 传感器、程序、工具和阿木 | 真正的工具执行层 |
| 反复“观察—判断—执行—回传” | Agent Loop |
| 六轮上限、断电规则、人工确认和安全线 | Guardrails：权限、预算、步数、超时和完成条件 |
| 短时间复用不变的记录前缀 | Prompt Cache / Prefix Cache |
| 黑匣子外面的整套维修系统 | Agent，也就是改造完成后的“百事通” |

### 2. 一次调用、Chat 和 Agent，本质上调用的仍是同一个模型

最简单的调用只需要：

> 用户问题 → 模型 → 回答

在工程上，这完全可以只是一条 curl 或 HTTP 请求：Endpoint 指定请求送到哪里，API Key 负责鉴权，Model 指定使用哪个模型，Messages 则装着这次真正交给模型的上下文。

Chat 没有改变模型的基本工作方式，只是把输入组织成一组有角色和顺序的消息，例如：

- system：系统规则和身份
- user：用户问题
- assistant：模型以前的回复
- tool：工具执行结果

Temperature、max_tokens、stream 等参数可以继续控制输出的发散程度、最大长度和返回方式，但它们不会自动为模型增加记忆、工具或执行能力。

到了 Agent，底层仍然是在发送模型请求。区别是每次请求里可能还会拼入：

- 历史消息与当前任务状态
- 检索到的文档、代码或网页
- Skills 提供的方法和规则
- Tools 的名称、描述与参数结构
- MCP 暴露的工具和资源说明
- 前几轮工具调用的结果
- 用户这一次的新问题

因此，Agent 并不是把一次调用替换成另一种神秘计算，而是让外层程序不断准备更合适的输入，并接住模型输出继续工作。

### 3. 模型本身无状态，状态保存在应用外层

百事通无法理解“刚才的方法”，对应的是模型通常不会在一次请求结束后自动保存会话。

Chat 看起来能够记住前文，是因为应用把之前的消息保存下来，并在下一次请求时重新发送。Agent 看起来能够记住任务进度，也是因为外部系统保存了：

- 历史对话
- 工具调用与返回结果
- 已经完成的步骤
- 中间文件和工作区状态
- 用户偏好或长期记忆

所以更准确的表达是：

> 无状态模型 + 外部状态保存 + 每轮重新注入 = 看起来有状态的 AI 应用

模型看到的内容越完整，它越可能作出符合当前局势的判断；但上下文更多不等于事实一定正确。错误、过期或互相矛盾的材料，同样会把模型带向错误答案。

### 4. Tool Calling 只是动作意图，不是动作本身

百事通提出“读取压力”或“拆开过滤网”，并不表示这些动作已经完成。这对应 Tool Calling 的职责边界：

1. 模型根据上下文判断是否需要工具。
2. 模型输出工具名称和参数。
3. 外部程序验证参数、权限与风险。
4. 程序真正执行搜索、读取文件、访问接口或写入数据。
5. 程序把结果作为新的消息回传模型。

模型负责提出下一步，程序负责真实执行。把这两者混为一谈，会让权限、错误处理和安全边界全部失控。

Tools、Skills 和 MCP 也不是让模型“凭空获得新智能”：

- **Tool** 提供可以执行的能力。
- **Skill** 提供做事的方法、规则或领域知识。
- **MCP** 提供连接与描述外部工具、资源的标准方式。

它们最终都会以工具定义、文字说明或执行结果的形式进入模型上下文。

### 5. Agent Loop 让一次建议变成可持续执行

单次 Chat 通常到回答为止。Agent Loop 则把一次调用放进闭环：

> 观察当前上下文 → 模型决策 → 调用或执行工具 → 回传结果 → 再次决策

这个循环不能无限运行。至少应该明确：

- 最大步数
- 总超时时间
- Token、费用或工具调用预算
- 成功条件
- 高风险操作的授权方式
- 工具失败、参数错误和证据不足时如何退出

故事中出水量连续十分钟高于安全线后，程序立即停止，就是成功条件触发后的正常结束。如果没有停止条件，一个 Agent 可能死循环、不断消耗预算，也可能在任务已经完成后继续制造风险。

### 6. 上下文不是越多越好

不断把所有原文、日志和工具结果塞回模型，会造成上下文膨胀：

- 请求更慢、费用更高
- 关键信息被噪声淹没
- 重复内容增加
- 缓存更难命中
- 更容易超过上下文窗口

因此，真实系统通常需要区分：

- 稳定不变的系统规则和工具定义
- 需要长期保存的任务状态
- 本轮真正相关的检索材料
- 可以摘要的旧工具结果
- 必须保留原文以便核验的证据

这不是简单地“喂得越厚越好”，而是要让上下文完整、相关、可追溯，并控制噪声。

### 7. 缓存复用的是重复前缀，不是最终答案

故事里短时间复用不变的任务记录前缀，对应 Prompt Cache 或 Prefix Cache。

当多次请求的前半部分保持相同，例如 system prompt、tools schema、skills 说明和稳定的历史前缀，模型服务可能复用这部分已经计算过的处理结果。因此首字延迟和费用可能下降。

但缓存通常不意味着“这次不用思考，直接拿出上次回答”。新的用户问题、最新工具结果和最终输出仍然需要计算。缓存还通常具有有效期，并且对内容、顺序和格式敏感。把时间戳、随机 ID 等动态字段放进稳定前缀，也可能破坏命中。

### 8. 什么时候才真的需要 Agent

如果任务只是解释概念、改写文本或生成一份草稿，单次调用或 Chat 往往已经足够。

当任务同时具备下面几项特征时，Agent 才开始有价值：

- 必须读取外部资料或最新信息
- 必须操作文件、接口或其他真实系统
- 下一步取决于前一步结果
- 需要多轮纠错和验证
- 需要持续保存任务状态
- 需要明确的权限、预算与停止规则

第一个 Agent 不应该从“万能助手”开始。更稳妥的实施方式是：

1. 选择一个窄任务。
2. 只提供一个或少量工具。
3. 写清工具名称、描述和参数约束。
4. 设置最大步数、超时与成功条件。
5. 记录每轮输入、工具调用、结果和停止原因。
6. 用可验证任务测试完成率、工具选择准确率、耗时和成本。

这时可以把全文压缩成一个公式：

> Agent = Model + Instructions + Tools + State + Loop + Guardrails

模型仍然是负责理解和生成的核心，但真正让它从“会回答”走向“能围绕目标持续行动”的，是模型外面的工程系统。

### 9. 这则寓言简化了什么

为了让故事保持清楚，寓言把模型和模型服务压缩成了一个黑匣子。真实应用通常还需要通过 Endpoint、API Key 和请求参数访问模型。

传感器、摄像头和工具也不会自动连接。开发者需要实现 Tool Schema、参数校验、权限控制、错误处理和执行结果回传。MCP 可以统一其中一部分连接方式，但不会替代具体工具和安全设计。

最后，模型提出的下一步始终可能出错。Agent Loop 的意义不是保证正确，而是让系统能够取得新证据、验证结果、修正下一步，并在风险或成本超过限制时停止。

## 系列故事主线

“百事通”会作为前三章共同的故事主角，场景和人物保持不变：

1. **第一章：百事通的眼睛和手**

   阿木和小禾为黑匣子加入任务记录、工具、执行循环和安全边界，让它从只会回答的大模型变成 Agent。

2. **[[02. 检索、RAG 与知识系统|第二章：百事通的书架]]**

   百事通遇到自己没有读过的最新资料，阿木和小禾开始建立一套能够检索、引用、更新和追溯的外部知识系统。

3. **[[03. 构建个人知识库大纲|第三章：百事通开始理解阿木]]**

   百事通拥有公共知识后，仍然不了解阿木的项目、经验和习惯。他们开始整理个人笔记、记忆和工作记录，建立个人知识库。
