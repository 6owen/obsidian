# 从一次 Chat 调用到为什么需要 Agent

> [!note]
> 这一篇先不讲框架，也不急着写复杂代码。目标只有一个：把大模型、Chat 和 Agent 这三个概念放到同一条链路里，看清它们分别解决什么问题。

## 先看一个最小调用

像下面这样的一条请求，其实已经是最小可用的大模型应用了：

```bash
curl https://llmapi.isrc.ac.cn/v1/chat/completions \
  -H "Authorization: Bearer $NEW_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "DeepSeek-V4-Flash-0731",
    "messages": [
      {
        "role": "user",
        "content": "Explain quantum entanglement in one paragraph."
      }
    ],
    "temperature": 0.7
  }'
```

它做的事情非常直接：

- 你给模型一段上下文。
- 模型根据上下文生成回复。
- 服务把这段回复再返回给你。

到这里为止，我们已经完成了“调用大模型”这件事。但也正因为它足够简单，所以它的边界会非常清楚：它能回答，不代表它能行动。

## 大模型是什么

大模型（LLM，Large Language Model）可以先粗暴地理解成一个经过大规模训练的“语言与模式生成器”。

更准确一点说，它的核心能力是：根据你给它的上下文，预测接下来最合理的内容。这个“内容”不一定只是自然语言，也可能是代码、表格、JSON、SQL，甚至某种固定格式的操作步骤。

所以大模型擅长的，通常是这几类事：

- 理解一句话大概在说什么。
- 把零散信息整理成结构化表达。
- 根据规则生成内容，比如代码、文案、摘要、分类结果。
- 在不完全确定的情况下，给出“看起来合理”的下一步。

但它也有几个天然限制：

- 它默认不知道你电脑里的文件。
- 它默认不知道刚刚发生的最新事件。
- 它默认不能替你点击按钮、发请求、改数据库。
- 它也不会自动把这次对话永久记住。

所以，大模型更像是一个很强的“推理与生成核心”，而不是一个完整应用。

## Chat 是什么

很多人第一次接触大模型时，接触到的其实不是“模型本身”，而是 Chat 这种调用方式。

在 API 层面，Chat 的意思通常是：你不是只传一段 Prompt，而是把输入组织成一组消息（messages），例如：

- system：系统要求
- user：用户输入
- assistant：模型之前的回复

这样做的好处是，模型会在“对话上下文”里理解任务。哪怕你只问一句话，也可以用 Chat 的格式来调用。

所以可以这样区分：

- 大模型：是能力核心。
- Chat：是最常见的交互封装。
- Chatbot：是基于 Chat 做出来的产品形态。

也就是说，Chat 解决的是“怎么和模型说话”，不是“怎么让模型真的去做事”。

## Agent 是什么

如果把大模型看成大脑，那 Agent 就更像是一个围绕大脑搭起来的“执行系统”。

一个实用的理解公式是：

```text
Agent = Model + Instructions + Tools + State + Loop + Guardrails
```

这里面每一部分都很重要：

- Model：负责理解、推理、生成。
- Instructions：告诉它目标、边界和行为方式。
- Tools：给它查询、搜索、读文件、写文件、调用接口等能力。
- State：保存当前任务上下文、中间结果、记忆或工作区状态。
- Loop：让它不是只回答一次，而是能持续“观察 → 决策 → 执行 → 再观察”。
- Guardrails：限制权限、预算、步数、风险操作，避免乱跑。

所以 Agent 不是一个“更聪明的模型”，而是一个让模型可以围绕目标持续工作的系统。

## 为什么单次 Chat 不够

单次 Chat 调用很强，但它本质上还是“一次输入，一次输出”。很多真实任务并不是这样完成的。

比如下面这些需求：

- “帮我看看这个仓库里哪里在调用支付接口。”
- “查一下官方文档最新写法，再帮我改这段代码。”
- “读取我今天的会议记录，总结后写进 Obsidian。”
- “先查资料，再比较方案，最后给出执行计划。”

这些任务有一个共同点：它们都不是只靠脑补就能完成的，而是要和外部世界发生交互。

这时单次 Chat 的问题就暴露出来了：

| 需求 | 单次 Chat | Agent |
| --- | --- | --- |
| 概念解释、改写、摘要 | 很适合 | 也可以，但常常没必要 |
| 获取最新网页信息 | 不行，除非你手动提供 | 可以，通过搜索或浏览工具 |
| 读取本地文件、代码仓库 | 不行，除非你手动粘贴 | 可以，通过文件工具 |
| 执行真实操作 | 不行 | 可以，在授权范围内调用工具 |
| 多步拆解任务 | 只能靠一轮回答硬写出来 | 可以边做边调整 |
| 根据结果继续下一步 | 需要你人工接力 | 可以在循环里继续 |
| 控制预算、权限、停止条件 | 很弱 | 可以系统化约束 |

一句话总结就是：

> Chat 让模型能回答，Agent 让模型能围绕目标持续行动。

## 从 Chat 到 Agent，中间到底多了什么

这条演化路径其实很自然：

### 1. 只有模型调用

你发一句话，模型回一句话。

这时最适合做：

- 问答
- 总结
- 改写
- 翻译
- 简单代码生成

### 2. 加上多轮 Chat

你把历史消息也一起传进去，模型能“接着聊”。

这时它开始像一个助手，但本质上仍然主要是在生成文本。

### 3. 加上 Tool Calling

模型不只是回答“最终答案”，而是可以先说：

“我想调用搜索工具。”

或者：

“我想读取这个文件。”

注意，这里模型只是提出调用意图，真正执行工具的还是外部程序。也就是说，Tool Calling 不是工具执行本身，而是模型对外表达动作需求的一种协议。

### 4. 加上 Agent Loop

程序接到模型的工具调用请求后：

1. 验证参数。
2. 真正执行工具。
3. 把结果回传给模型。
4. 让模型决定下一步。
5. 重复这个过程，直到任务完成或触发停止条件。

到这里，Agent 才真正开始成形。

## 一个直观例子

假设你要做的不是“解释量子纠缠”，而是：

> 帮我查一下某个框架最新的官方文档写法，再结合我本地项目里的代码，给出修改建议，并把结论写成一篇笔记。

如果只有一次 Chat 调用，你需要自己完成这些动作：

- 打开浏览器查文档。
- 复制文档内容给模型。
- 打开本地代码。
- 复制代码给模型。
- 再把结果手动保存到笔记里。

如果是 Agent，这些动作就可以被系统接起来：

1. 先理解你的目标。
2. 调搜索工具找官方文档。
3. 调文件工具读取本地代码。
4. 比较新旧写法。
5. 生成修改建议。
6. 写入目标笔记。
7. 必要时继续补充或修正。

这时模型仍然是核心，但整个系统已经不再只是“聊天”。

## 什么时候其实不需要 Agent

Agent 很有用，但不是所有任务都应该上 Agent。

如果任务具备下面这些特点，普通代码、脚本或单次模型调用往往更合适：

- 输入固定，输出格式固定。
- 处理步骤明确，不需要临场判断。
- 不需要外部搜索、读写文件或调用真实工具。
- 风险高，必须完全确定性执行。
- 你只是想要一个解释、一段摘要或一份草稿。

一个常见误区是：只要用了大模型，就想把所有事情都叫 Agent。其实更实用的判断标准是：

> 当任务需要“根据环境反馈继续决策和执行”时，Agent 才真正有必要。

## 这篇先记住三个结论

1. 大模型不是 Agent，它只是 Agent 的推理核心。
2. Chat 不是 Agent，它只是最常见的模型交互方式。
3. Agent 的关键不是“更会说话”，而是“能围绕目标持续调用能力并完成任务”。
