# 从模型调用到工具调用

> [!note]
> 这一篇要解决的，是从“模型只会说话”到“模型开始表达动作意图”这一步。真正的关键不是模型有没有手脚，而是你有没有给它一套可被程序接住的动作协议。

## 1. 回答和行动之间差了什么

![[assets/01-03-tool-calling-illustrations/01-tool-switchboard.svg]]

如果只有普通对话调用，模型最多只能这样回答：

> 你可以去搜索一下官方文档。

这句话有用，但它只是建议，不是执行。

想让系统真的动起来，至少还差一层：

- 模型不仅要会“说”
- 还要会“表达我现在想调用哪个工具、带什么参数”

这就是 Tool Calling 出现的原因。

## 2. Tool Calling 是什么

Tool Calling 可以先用一句话理解：

> 模型不直接执行工具，而是输出一个结构化的“调用意图”，程序再去执行。

它不是模型自己真的去打开网页、读取文件或写入数据库，而是模型先生成一份动作请求，程序负责接住它。

## 3. Tool Schema 要描述什么

如果你想让模型调用工具，首先得把工具定义清楚。

一个最小工具定义里，通常至少要有这些信息：

- 名称：这个工具叫什么
- 描述：它是做什么的
- 参数：调用它时需要什么输入
- 参数约束：这些输入是什么类型、哪些是必填

例如，一个最小搜索工具可以这样描述：

\`\`\`json
{
  "type": "function",
  "function": {
    "name": "search_docs",
    "description": "Search the documentation and return relevant passages.",
    "parameters": {
      "type": "object",
      "properties": {
        "query": {
          "type": "string",
          "description": "The search query."
        }
      },
      "required": ["query"]
    }
  }
}
\`\`\`

## 4. 模型会返回什么样的调用意图

当模型判断“我需要先用工具”，它可能不会直接给最终答案，而是返回类似下面这样的结构：

\`\`\`json
{
  "role": "assistant",
  "tool_calls": [
    {
      "id": "call_001",
      "type": "function",
      "function": {
        "name": "search_docs",
        "arguments": "{\\"query\\":\\"OpenAI-compatible chat completions tools\\"}"
      }
    }
  ]
}
\`\`\`

这里要特别注意：

- 模型返回的是“我要调用谁”和“我要传什么参数”
- 这一步仍然没有发生真正的工具执行

## 5. 真正执行工具的是谁

工具执行永远是外部程序的责任。

程序通常要做这几步：

1. 读取模型返回的 tool call。
2. 解析参数。
3. 做参数校验。
4. 调真正的业务函数或外部接口。
5. 把结果包装成 tool result。
6. 再回传给模型继续判断。

所以 Tool Calling 的真正价值，不是让模型“自己动手”，而是让模型可以参与一个可控执行链路。

## 6. Tool Calling 不等于工具执行

这是最容易混淆、但也最重要的一点。

请把它死记住：

> Tool Calling 是模型提出调用意图，不是工具已经执行完成。

更准确的职责边界应该是：

| 角色 | 负责什么 |
| --- | --- |
| 模型 | 判断要不要用工具、该用哪个工具、参数大概怎么填 |
| 程序 | 验证、执行、限权、记录、回传结果 |

## 7. 常见坑

- 工具描述写得太空
- 参数 schema 太松
- 工具太多
- 执行层没有兜底

工具一多，错误并不会消失，只会换一种方式出现。

## 8. 这篇先记住什么

1. Tool Calling 是模型输出结构化动作意图，不是工具已经执行。
2. 工具 schema 是模型理解“有哪些能力可用”的入口。
3. 真正执行工具、校验参数、控制权限的，永远是外部程序。
4. Tool Calling 把模型从“只会回答”推进到“可以参与执行链路”。
