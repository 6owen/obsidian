# Memory 实现原理：谁在什么时候写记忆

> [!note]
> 用 Mastra 时配置一下 `new Memory({...})` 就有记忆了，用 OpenClaw 时知道"Markdown 是本体、SQLite 是索引"，但配置可用和知道原理之间隔着一层：到底是谁、在什么时候、把什么写进了哪里？这一篇把两家的 memory 拆到"触发器 / 写入者 / 存储位置"的粒度，专门回答那些"配置用得飞起、原理一脸模糊"的问题。

## 1. 先给总表：Mastra 的四个子系统

Mastra 的 `Memory` 其实是四个独立子系统的组合，它们的触发方式和存储位置完全不同：

| 子系统 | 干什么 | 谁触发 | 写到哪 |
| --- | --- | --- | --- |
| Message History | 保存当前对话原文 | 每次 API 调用自动 | storage DB（LibSQL/PG…） |
| Working Memory | 一小块常驻状态（用户名、偏好、目标） | **主 Agent 自己调工具** | thread metadata / `mastra_resources` 表 |
| Semantic Recall | 按语义检索历史消息（RAG） | 每条新消息自动（默认关闭） | 向量库 + embedding |
| Observational Memory | 后台小模型压缩历史为观察日志 | **token 阈值**（30k/40k） | storage DB |

一个关键纠正：这四个里**只有 Observational Memory 在"总结"**。Working Memory 是主模型主动写，Semantic Recall 只检索从不生成，Message History 就是原文堆放。

## 2. Message History：没有总结，只有原文

这是最简单的一个：每轮对话的消息（用户、助手、工具调用和结果）原样存进 storage 数据库，按 `threadId`（会话）和 `resourceId`（用户）组织。下次调用时取最近 N 条塞回上下文。

它不做任何加工。唯一会"处理"它的是 Observational Memory——超过阈值后把旧消息压缩成观察。

所以"对话历史"和"记忆"在 Mastra 里是两回事：前者免费自带，后者要显式开。

## 3. Working Memory：不是后台总结，是 Agent 自己调工具

这是最容易被误解的一个。Working Memory 是一块 Markdown 文本（或 Zod schema 定义的 JSON），**由主 Agent 在对话过程中通过 `updateWorkingMemory` 工具自己更新**。

回答"什么时候触发"：

- 不是每条消息触发一次——是每轮对话里模型都"有机会"调用这个工具，调不调由它自己判断
- 不是某个时间段触发——没有任何定时器
- 也没有一个监听模型在后台看着——就是主模型自己

用户说"我叫 Sam，在柏林"，模型觉得这值得记住，就调工具把模板里的空填上：

```
# User Profile
- Name:
- Location:
--- 用户说完 "My name is Sam and I'm from Berlin" ---
# User Profile
- Name: Sam
- Location: Berlin
```

几个实现细节：

| 维度 | 做法 |
| --- | --- |
| 模板 vs Schema | 模板是 Markdown，**整体替换**语义；Schema 是 JSON，**深度合并**语义（只传要改的字段，传 null 删除） |
| 模板放哪 | 注入 system prompt，所以每次更新都会打穿 prompt cache（有代价） |
| 作用域 | resource 级（默认，跨所有 thread 共享）或 thread 级（每会话隔离） |
| 存储 | thread metadata 的 `workingMemory` 字段；resource 级需要支持 `mastra_resources` 表的存储适配器 |
| 只读模式 | `readOnly: true` 给路由 Agent、子 Agent 用——看得到改不了 |

除了让主 Agent 自己管，还有两条路：程序化直接调 `memory.updateWorkingMemory()`；或者开启 OM 的 `observation.manageWorkingMemory: true`，把维护权交给后台 Observer（主 Agent 不用再惦记这事，还能把 working memory 挪出 system prompt 保住缓存）。

## 4. Semantic Recall：只做检索，从不总结

第二个常见误解："Semantic Recall 和 Observational Memory 是通过一个小模型自主选择的。"

实际机制是纯 RAG，全程没有 LLM 做选择：

1. 新用户消息进来 → embedding → 去向量库查相似的历史消息（topK 条，每条带前后 messageRange 条邻居）
2. 命中的消息注入上下文
3. LLM 回复完成后 → 本轮所有新消息（用户、助手、工具调用和结果）全部 embedding 后写进向量库

"自主选择"的感觉来自 embedding 相似度——它在语义空间里挑了相关的，但没有任何模型在推理"这条该不该记"。

配置项也就都是检索参数：`topK`、`messageRange`、`scope`（thread 还是 resource 范围）、metadata `filter`（按线程元数据过滤）。默认关闭，因为每轮多一次 embedding + 向量查询的延迟。

## 5. Observational Memory：真正在"总结"的是两个后台小模型

OM 是 Mastra 里唯一名副其实的"记忆总结系统"，由两个后台 Agent 组成：

- **Observer（观察者）**：盯着对话，把旧消息压缩成带时间戳的简短笔记
- **Reflector（反思者）**：观察日志太长时，整体重写压缩

### 5.1 触发：token 阈值，不是消息条数，不是时间

| 阈值 | 默认值 | 触发什么 |
| --- | --- | --- |
| `observation.messageTokens` | 30,000 | 消息历史超过 → 激活观察，旧消息被移出上下文 |
| `reflection.observationTokens` | 40,000 | 观察日志超过 → Reflector 重写整个日志 |

### 5.2 异步缓冲：为什么不卡顿

默认开启 async buffering：对话增长过程中，每积累约 20% 阈值（约 6k token）就在**后台**跑一次 Observer，产出先存进缓冲区。等真正到 30k 阈值时，缓冲的观察"瞬间激活"，对应旧消息移出上下文，只留约 20% 阈值的近期历史（约 6k）。**主 Agent 全程无感，不会停下来等总结。**

还有两个聪明的激活时机：

- `activateAfterIdle: 'auto'`：按当前 provider 的 prompt cache TTL 判断——缓存反正要过期了，下次请求前先激活压缩版上下文
- `activateOnProviderChange: true`：换模型前先激活，因为换了 provider 旧缓存必然作废

### 5.3 观察日志长什么样

```
Date: 2026-01-15
- 🔴 12:10 User is building a Next.js app with Supabase auth, due in 1 week
- 🔴 12:10 App uses server components with client-side hydration
- 🟡 12:12 User asked about middleware configuration for protected routes
```

压缩比通常 5–40 倍（Playwright 一页 50k token 的 snapshot 变成几百 token 的观察）。Observer 还维护"当前任务"和"建议回复"，保证上下文被压缩后接得上话。

### 5.4 Reflector：重写而不是追加

观察日志到 40k 时，Reflector 把**整个日志**重写一遍：老信息压得更狠、近期细节保留。每次反思的输出就是新日志，不是越积越厚的独立层——所以无论对话跑多久，记忆体积有界。

### 5.5 存储

全部在数据库里（OM 只支持 pg/libsql/mysql/mongodb/convex/oracledb 适配器），没有任何文件形态。默认模型 `google/gemini-2.5-flash`，推荐大上下文 + 便宜的快模型，还支持按输入 token 分层选模型。开启 `retrieval` 后，每条观察记录消息 ID 区间，Agent 可以用 `recall` 工具翻回被压缩掉的原文——压缩不丢底账。

## 6. Mastra 小结：一张"触发器"对照表

| 子系统 | 什么时候写 | 谁写 | 代价模型 |
| --- | --- | --- | --- |
| Message History | 每轮自动 | 框架 | 存储便宜，上下文膨胀 |
| Working Memory | 模型自己决定调工具 | 主 Agent | 每次更新打穿 prompt cache |
| Semantic Recall | 每条新消息（查询+写入） | 框架 | 每轮 embedding 延迟 |
| Observational Memory | token 阈值 + 后台缓冲 | Observer/Reflector 小模型 | 后台 LLM 调用，主流程零停顿 |

一句话：Mastra 把"记忆的智力"放在**两个常驻后台小模型**上，用 token 阈值驱动，换来的主流程不停顿。

## 7. OpenClaw：MEMORY.md 是怎么"来"的

换到文件优先的 OpenClaw，同样的三个问题——怎么写、何时触发、存在哪——答案换了一套形态。写路径分三条：

### 7.1 工作层：memory/YYYY-MM-DD.md（主 Agent 自己写）

先回答"md 是谁写的"：**日常记忆 md 的主要作者就是主 Agent 自己**。它生成的 workspace instructions 里明确鼓励它边干活边把耐久事实记下来——md 就躺在它自己的 workspace 里，它本来就有文件工具，写记忆和写代码是同一双手。dreaming 只负责后台整合。

写入有三个时机：

- **随时**：Agent 在会话中主动记录观察和上下文（指令引导）
- **压缩前**：上下文要 compaction 之前，系统插入一个静默轮（silent turn）提醒它把重要内容存盘，默认开启——这个家务轮还能单独钉一个便宜本地模型跑
- **会话结束**：内置的 session-memory hook 把会话小结写成 `memory/YYYY-MM-DD-<slug>.md` 变体文件

读取侧的配套设计：**今天和昨天**的日记在 `/new` 或 `/reset` 开新会话时自动加载，更老的日记只进索引、靠 `memory_search` 检索——"工作层只建索引不注入"的准确含义就是这个（最近两天除外）。

另一条容易混淆的流：**会话转录不会直接变成 md**。转录（脱敏后、只限交互式会话）被摄取进 SQLite 短期信号库，已召回过的内容还会被标记防止"把自己回忆出来的话再学一遍"——它是做梦排序的机器原料，不是给人读的文件。

### 7.2 长期层：MEMORY.md（每天最多被 dreaming 写一次）

这是关键答案：**MEMORY.md 不是每次会话都更新的**。只有做梦（dreaming）的深睡阶段晋升才能写它，默认 cron 是每天凌晨 3 点跑一次完整扫描（light → REM → deep 三阶段，只有 deep 落盘）。

一道候选要进 MEMORY.md，先过三道硬门槛：

```
minScore（加权分数）+ minRecallCount（被召回次数）+ minUniqueQueries（查询多样性）
```

分数由六个加权信号算出：

| 信号 | 权重 |
| --- | --- |
| 相关性（平均检索质量） | 0.30 |
| 频率（累积了多少短期信号） | 0.24 |
| 查询多样性（多少不同语境召回过它） | 0.15 |
| 近期性（时间衰减） | 0.15 |
| 巩固度（跨多天反复出现） | 0.10 |
| 概念密度 | 0.06 |

过门槛的候选交给一个**整合子代理**连着现有 MEMORY.md 一起重写，重写有四条护栏：最多丢 25% 旧条目、每条新条目必须带 `Source: path#Lx-Ly` 来源引用、不能超注入预算、结构解析必须通过。模型不可用或校验失败时，退回逐条追加的安全路径。改文件之前，旧版 MEMORY.md 先存进 SQLite（preimage），变更报告写进 DREAMS.md 供人审阅。晋升成功的条目还带两个隐藏注释：触发短语和重要度 1–10，供后面召回用。

### 7.3 指令层：USER.md

用户画像层：稳定偏好、沟通风格、关系、活跃项目，写成命令式指令（directive），每条带观察日期和 active/superseded 元数据。关键纪律是**偏好变了就地取代（supersede in place），不是追加一条相反的新指令**——所以它永远只有一个"当前生效"的版本，不会像流水账一样自相打架。加载时有独立的小预算，和 MEMORY.md 分开注入。

## 8. OpenClaw：怎么隔离

三层隔离：

| 层 | 做法 |
| --- | --- |
| Agent 间 | 每个 Agent 一个独立 SQLite：`~/.openclaw/agents/<agentId>/agent/openclaw-agent.sqlite`，workspace 各归各 |
| 信任间 | 每个 chunk 带 provenance（`owner` / `agent` / `untrusted` / `system`），**存在 SQLite 里而不是 Markdown 里**——被召回的正文无法改写自己的信任级别 |
| 晋升前 | 污点门：provenance 是 `untrusted` 或 `system` 的候选直接进不了整合子代理，这不是扣分，是一票否决 |

注意最后一条的设计感：信任元数据和正文物理分离，防止提示词注入借道记忆系统自我提权。

## 9. OpenClaw：怎么召回

`memory_search` 是混合检索，两路并行再合并：

```
向量检索（语义） ┐
                ├→ 加权合并 → 时间衰减 → 重要度乘数 → MMR 去冗余 → 结果
BM25 关键词（FTS5，CJK 用 trigram） ┘
```

细节：

- 索引粒度：400 token chunk，80 token 重叠，覆盖 MEMORY.md、USER.md、memory/*.md
- 排序公式：`混合相关性 × 时间衰减 × 重要度`。日期命名的日志按 30 天半衰期衰减，MEMORY.md 和 USER.md **常青不衰减**（这也是为什么脏东西进了 MEMORY.md 就赖着不走——策展纪律重要）
- MMR（λ=0.7，Jaccard 重叠）去冗余：五条结果都讲同一个路由器配置时，宁可选一条内容不同的
- **触发短语召回**：入站消息和条目上存的短触发短语做确定性匹配（预过滤走现有关键词+向量路径，**不跑模型**），强匹配最多注入 3 条进隐藏上下文。只有 root MEMORY.md / USER.md 里的可信条目有资格自动注入，日志和导入内容永远只能靠显式工具调用
- 文件监听：markdown 变更后 1.5 秒防抖重建索引；全量重建在临时库里原子替换，失败不影响现有索引

## 10. 两种实现，同一个问题的两种解法

| 维度 | Mastra | OpenClaw |
| --- | --- | --- |
| 真相形态 | 数据库行 | Markdown 文件 |
| 总结触发 | token 阈值（同步事件驱动） | cron 定时（默认每日） |
| 模型在哪 | 两个常驻后台小模型 | 一次扫描里的整合子代理 |
| 写入护栏 | 阈值 + 缓冲 + 重写校验 | 三道分数门槛 + 四条重写护栏 + 污点门 |
| 可审查性 | Studio UI 看进度条和日志 | DREAMS.md 人可读报告 + git |
| 锁定风险 | 换框架要迁数据库 | 文件搬走就行，索引重建 |

殊途同归的部分更值得注意：两家都做了**压缩、门槛、可审查**这三件事——都用小/便宜模型做总结而不是主模型，都拒绝无门槛写入，都留了事后审查的账本。区别只在"记忆的本体放在哪"这一个根本选择上，其他一切都是这个选择的推论。

## 11. 这篇先记住五个结论

1. Mastra 四个子系统里只有 Observational Memory 在"总结"；Working Memory 是主 Agent 自己调工具写的，Semantic Recall 是纯 embedding 检索。
2. OM 的触发是 token 阈值（30k 观察 / 40k 反思）+ 后台异步缓冲，主流程零停顿；Reflector 每次整体重写日志，记忆体积有界。
3. OpenClaw 的 MEMORY.md 每天最多被 dreaming 写一次：三道分数门槛、六信号加权、整合子代理带护栏重写、旧版先备份、报告进 DREAMS.md。
4. OpenClaw 的隔离靠 per-agent SQLite + 与正文物理分离的 provenance 信任标记 + 晋升前一票否决的污点门。
5. 召回两家同构：混合检索 + 时间衰减 + 多样性去重；OpenClaw 额外的触发短语召回全程不跑模型。
