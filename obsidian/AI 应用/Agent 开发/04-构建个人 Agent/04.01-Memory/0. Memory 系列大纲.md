# Memory 系列大纲：理解并实现文件型 Agent Memory

> [!note] 已确定的方向
> 第一篇投石问路：讲清基础，介绍 OpenClaw、Claude Code、pi Agent、Mastra，并补充其他开源 Memory 方案的对照。第二篇明确自己想做的 Memory 要达到什么目的、采用什么方法。后面暂按四篇实现文章安排，总计约六篇，可按实际开发进展微调。
> 自己实现时参考 OpenClaw 的文件记忆思路：**文件是记忆本体，SQLite、全文和向量索引是可重建的派生数据。** Mastra 是当前开发背景、对照案例与后续接入对象。

## 1. 系列定位与边界

这个系列记录我对 Agent Memory 的理解，以及如何构建自己能够掌控的记忆系统。先让读者看见全貌，再给出自己的选择，最后用实现说明这些选择怎样落地。

以“Agent ≈ 模型 + harness”建立工程视角：模型负责根据输入推理，harness 组织调用循环、工具和上下文等能力，memory 是其中一部分。读写文件、编辑和 Bash 是可能提供的工具，不要求每种 Agent 都具有同一套工具。

本系列的 Memory 指应用层记忆：把过去的信息保存、维护，并在未来需要时重新交给模型。普通推理调用不自动把对话写入模型权重；模型的参数知识、当前上下文和持久化记忆需要区分。

读者既包括想理解 Agent 记忆的人，也包括准备自己开发的工程师。第一篇独立成文，后续逐渐增加实现细节。基础、比较可以放在同一篇，靠控制深度保持可读性，不为每个概念单独开篇。

## 3. 第一篇：基础认识与实现对照

工作标题：**没有记忆的模型，怎么做出有记忆的 Agent**。

现有起稿：[[1. 没有记忆的模型，怎么做出有记忆的 Agent]]。正式写作按以下结构展开，现有文件仍保留为起稿。

### 第一部分：为什么 Agent 需要 Memory

- 从一个具体场景切入：之前讨论过的偏好、决定或任务进度，换一次会话后怎样继续使用？个人经历需要有真实材料，假设场景明确写“例如”。
- 解释模型与 harness 的分工，定位 Memory。
- 区分当前上下文、聊天历史和长期记忆；聊天历史可以是最简单的记忆实现，但保存过不等于每次都被读取。
- 解释跨会话连续性、有限窗口、成本和信息噪声。窗口上限与长上下文利用质量分开说。
- Prompt cache 只用短段落澄清计算复用与持久记忆的区别，不展开价格和过期参数。

### 第二部分：记忆最基本的工作方式

用一张图讲清：

```text
对话 / 工具结果 / 外部资料
          ↓ 选择、记录
      持久化记忆
          ↓ 读取、检索、筛选
    本次模型调用的上下文
          ↓
       回答与行动
          ↓ 产生新的可记录信息
```

只建立几组必要问题：保存什么、谁来写、什么时候写、放在哪里、如何被想起、怎样保持有效。这里不展开代码和算法。

### 第三部分：四个主要案例，以及其他开源 Memory

**四家各有独立小节，保持同一观察顺序**：记忆长什么样 → 谁在何时写入 → 如何进入上下文 → 能借鉴什么、有什么代价。每家选一张小图或一个文件/配置片段，不逐项复述文档。

| 案例 | 本节重点 | 深度边界 |
| --- | --- | --- |
| OpenClaw | 文件记忆、长期精选与过程记录、搜索和整理之间的关系 | 作为后续实现的主要参考；区分文件内容、索引与运行状态 |
| Claude Code | 项目指令与自动记忆的区别，记忆文件如何被维护和加载 | 不把 CLAUDE.md 和 auto memory 混为一谈 |
| pi Agent | 核心提供什么，会话持久化与跨会话记忆扩展如何分工 | 不把“没有某种内置长期记忆”写成“没有任何记忆” |
| Mastra | Message History、Working Memory、Semantic Recall、Observational Memory 分别解决什么问题 | 讲能力及读写机制，不堆 API 和阈值 |

四家之后用一个短小节补充**其他开源 Memory 方案**。候选调研对象：Mem0、Letta、Graphiti；正式写作核验定位、许可证与当前能力后选 2～3 个。目的在于补充视角，避免继续扩张成完整产品巡礼。完整 Agent 产品、框架和独立记忆组件不直接按功能数量排高低。

最后用一张总表收束，比较：

- 记忆本体与存储位置。
- 写入者、写入时机与整理方式。
- 固定加载、按需读取和检索召回。
- 作用域、可编辑性、可迁移性与维护成本。

尚未核验的格子保留“待核验”，不按印象补全。

### 第四部分：我的理解与下一步

收束到三个认识：记忆需要读写闭环；现有实现是在不同目标下做选择；我希望自己的记忆能直接查看、修改、带走，并能接入不同 Agent。

因此下一篇明确自己的目标，并选择文件作为记忆本体。第一篇只给出方向，详细目录、协议和实现留到后面。

**篇幅控制建议**：基础与流程约三成，四家及其他方案约六成，个人理解约一成。只是编辑预算，不是固定写作比例。基础压缩到够用，产品部分讲机制，不展开源码细节。

## 4. 第二篇：明确自己的目标与方法

工作标题：**设计自己的 Memory：目标、文件结构与读写方法**。

### 4.1 我想解决什么

根据当前方向，先提出以下目标，真实项目需求在写作时补实：

1. 跨会话保留有价值的信息，例如偏好、项目决定和任务背景。
2. 记忆能被人直接阅读、修改、备份和迁移。
3. Agent 能在需要时找到相关信息，而不是每次塞入所有文件。
4. 新事实能更新旧事实，生成的总结可以回到来源核查。
5. 接入方式与某个 runtime 分离，先在自己的 Mastra 项目中跑通。

验收场景先写清：新会话能找到旧决定；人工改动能在后续读取中生效；删除后不会再从旧索引召回；索引丢失后可以从文件恢复。

### 4.2 核心架构：文件本体 + 派生索引 + Agent 接口

```text
Agent / 人工输入
       ↓ 受控写入
记忆文件：内容、标识、来源、有效状态
       ↓ 扫描、切分、建立索引
SQLite / 全文索引 / 向量索引
       ↓ 检索命中
回读并核验当前文件 → 按预算组装上下文 → Agent
```

“序列化索引”在正文中使用更明确的表述：**持久化的、可重建的检索索引**。SQLite 是承载方式，可以保存全文索引、分块映射、内容哈希等，不是只把文本换一种编码存一遍。

本方案的约束：

- 所有需要长期保留、影响记忆含义的数据都落在文件中，包括来源、状态和纠正关系。
- 索引里的分块、向量、路径映射和哈希均可从文件及索引配置重新生成。
- 重建后检索可恢复；不承诺不同 embedding 模型或参数下排名完全一致。
- 修改以文件为准，再使索引失效或更新；避免文件和数据库双向各自修改内容。
- 将来若增加无法从文件还原的反馈或操作记录，要先设计文件落点；不能悄悄把索引变成第二份记忆本体。

这是一项自己的设计选择，不泛化为所有 Memory 都必须如此。

### 4.3 最小目录与职责

以下为方案示意，不代表本次创建目录：

```text
memory/
├── MEMORY.md          # 小而稳定的入口摘要与导航
├── notes/             # 按主题维护的长期记忆
├── journal/           # 按日期或来源追加的过程记录
└── index/             # SQLite 等派生索引，可重建
```

文件中保留稳定标识、所属用户或项目、来源、时间和状态；只使用当前确实需要的字段。文件改名时尽量不改变记忆标识。

Obsidian 中的 `obsidian/` 原始笔记仍归人类所有，`wiki/` 是派生层。可以接入读取，但不直接把原始笔记目录当成 Agent 随意追加的 journal。是否复用 Vault 作为实际存储，在实现时根据项目挂载方式决定。

### 4.4 定义读写与维护方法

- 读：少量入口加载，详细内容按需搜索和回读。
- 写：先显式记录，再逐步加入自动提取；限定可写路径和作用域。
- 整理：过程记录提炼为主题记忆；保留来源和纠正依据。
- 更新与删除：修改文件，同步索引，检查旧内容是否仍可被召回。
- 接入：明确记忆读写工具或调用前后钩子的职责，第一版不要求跨工具全覆盖。

第二篇讲这些方法的理由、边界与接口轮廓，不提前展开四篇实现代码。

## 5. 后面四篇：怎样实现

### 第三篇：文件存储与最小读写闭环

**目标：不用数据库，也能完成写入、重启、新会话读取。**

- 建立文件组织、最小元数据与读写接口。
- 显式写入一条记忆，回读内容和来源，形成最小闭环。
- 区分过程记录、主题记忆和入口摘要。
- 实现基本的路径与作用域限制、原子写入；第一版可采用单写入者。
- 用少量文件固定加载或简单文本搜索，不提前引入向量库。

验收：重启后仍能读取；人工编辑后读到新内容；不同项目不误读；写入失败不留下半个文件。

### 第四篇：从文件搜索到混合召回

**目标：文件是本体，索引只是加速寻找文件内容。**

- 从关键词检索起步，再按实际需求增加向量和混合召回。
- 文件扫描、内容哈希、分块、稳定标识与来源映射。
- 增量更新与全量重建：处理修改、重命名和删除。
- 检索前限定作用域，命中后回读核验文件，去重并按上下文预算选取。
- 索引不可用时给出文本搜索等降级路径。

验收：语义问题与精确术语均有对照用例；旧索引不能复活已删除内容；移走索引后可从文件重建可用检索。

### 第五篇：记忆的提取、整理与更新

**目标：让记忆积累价值，而不是只积累文件。**

- 比较显式要求记住、主 Agent 调工具、后台提取三种写入方式，选择第一版所需范围。
- 从 journal 提取候选记忆，按价值、重复与来源决定是否进入 notes 或入口摘要。
- 实现去重、偏好更新、冲突记录、过期和删除。
- 参考 OpenClaw 的整理思路，区分压缩前保存、长期整理和从上下文移除。
- 自动整理保留变更记录和回退依据，模型推断不自动变成事实。

验收：同一偏好重复提及不反复新增；新偏好能替代旧偏好；整理后仍能找到决定依据；错误提取可纠正。

### 第六篇：接入 Agent 与实际验证

**目标：在自己的 Agent 中跑通完整链路，说明哪些能力实际有效。**

- 将独立的文件 Memory 接入 Mastra，选择工具调用或生命周期接入方式。
- 检查与 Mastra 自带历史或其他 memory 能力的职责，避免重复注入和重复写入。
- 展示一次完整过程：读取记忆 → 模型调用 → 工具执行 → 记录 → 下次召回。
- 从同一套文件接口说明其他 Agent 如何接入；可给一个轻量示例，不强求同时适配全部产品。
- 对比不启用记忆和启用记忆后的任务表现、上下文成本与延迟。
- 复盘尚未解决的问题，例如共享写入、更多数据来源或整理质量，不再自动拆出一批新文章。

验收：跨会话连续性、偏好更新、项目隔离、删除后不召回、索引重建后恢复、无答案时不编造。所有成绩以真实运行证据为准。
