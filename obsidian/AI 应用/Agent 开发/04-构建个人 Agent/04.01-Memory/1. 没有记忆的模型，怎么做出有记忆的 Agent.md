# 没有记忆的模型，怎么做出有记忆的 Agent

> [!abstract]- 文章结构图
> ![[1-memory-article-structure.excalidraw]]

## 1. 修车铺与一面会出主意的镜子

青石镇的春集还有七天，阿禾接下了十辆货车的修理生意。为了赶上交货，他借来一面镜子。据说，只要把问题和资料摊在镜前，它就能给出修车的办法。

第一辆车的轮子歪了。镜子看过尺寸，列出了拆轮、换轴、校正的步骤。阿禾很满意，照着做，车果然能走了。

可等他拿着方案去看第二辆车，才发现铺里没人量尺寸，仓库里的木料也还没搬出来。镜子已经答完了，十辆车仍然停在院子里。

阿禾叫来学徒小满，让他把这件事接起来：按镜子的要求查工单、量车轮、领材料，安排修理，再把试车结果送回来。镜子根据结果继续出主意，直到车修好。

铺子终于转了起来。可第二天，小满问“昨天那辆继续怎么修”，镜子又要他提供尺寸和客户要求。它懂修车，却不会自动带上这家铺子昨天发生的事。

阿禾不想再被追问，索性让小满把所有工单、对话和试车记录装成一册，每次连同新问题一起摊开。

这办法真管用。镜子能接着昨天的进度往下说。镜台还有一项便利：前面未改动的旧页，可以沿用上次验读的印记，少花一笔重复验读的钱。

阿禾于是把记录留得更全了。

到了第五天，工单已经铺不下。为了腾出地方，他让小满先拿走前几天的记录。偏偏其中一页写着：第三辆车后来改了尺寸，旧规格已经作废。镜子依据剩下的资料给了建议，工人照旧规格做了轴，到安装时才发现不合。

一下午的活得重做。春集只剩两天。

小满提议，把每辆车当前的尺寸、最后确认的要求和待办事项写在一张小卡上，旁边标出原工单的页码。每次先送这张卡和最新的试车记录；需要查理由时，再把对应工单找出来。

阿禾却舍不得：“少送这么多，它还能知道全吗？”

“那就留着原册。先把这辆车要用的找出来。”

整理也占工夫。两人每天收工后要核对新改动，给旧规格划上作废标记。有一次小满把“只改第三辆”抄成“全部改”，还得翻回原单纠正。

交货前，第三辆车再次送检。镜子看到更新后的卡片，给出了合适的调整步骤；小满让工人执行，把试车结果带回来，确认可以交付。

春集那天，十辆车按各自确认的规格交了出去。阿禾把镜子旁那摞小卡收好。这次帮他交上货的，除了镜子的主意，还有终于接得上的整套工作。

## 2. 已经能聊天了，为什么还需要 Agent

故事里的镜子对应模型：根据眼前的信息推理，给出回答或下一步建议。小满接起的那套工作，则对应模型外的运行系统——harness。

```text
Agent ≈ 模型 + harness
```

如果阿禾只想知道怎样修车，镜子的回答已经有用。可他的目标是把车修好。有人必须取得现场信息、执行操作、观察结果，再决定继续还是结束。

我们使用 ChatGPT、Claude、豆包、千问这类聊天入口时，也容易把两个层次合在一起：背后负责推理的模型，以及产品围绕模型提供的会话和其他能力。开发 Agent 时，需要把它们拆开看。

以“帮我修复一个 Bug”为例，模型可以分析代码、提出修改建议。但读取哪个文件、怎样执行修改、如何运行测试、失败后把什么结果送回模型，都需要外围系统来承接。模型产生工具调用请求，执行环境完成操作，再把结果返回，任务才有机会继续推进。[工具调用流程](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview)

**把所有资料交给模型，解决的是它这一次能看到什么；要让它持续完成任务，还要接起执行与反馈。**

你当然可以自己找文件、复制代码、运行命令，再把结果贴回聊天框。这时，你就在承担一部分 harness 的工作。把这些工作交给程序，才逐步得到一个能围绕目标行动的 Agent。

Harness 可以很简单：几个工具，加一个“调用模型 → 执行工具 → 返回结果”的循环。它也可以进一步负责权限、运行状态和上下文管理。Memory 是其中可以加入的一项能力，不是所有 Agent 都必须具备的前提。

但故事里还有一个合理的办法：每次都带上完整记录。既然它确实能让镜子接着昨天工作，为什么还要专门整理记忆？

## 3. 全部上下文加上缓存，不就够了吗

**在历史不长、信息完整、成本可以接受时，这样做完全可以。**

模型不必把项目经历写进自己的权重。只要你把过去的消息再次放进输入，它就能依据这些内容继续推理。保存历史并在下一轮重放，本身就是一种基础记忆机制，不需要先安装一个叫 Memory 的组件。

例如，在普通的消息回放方式下：

```text
第一次：项目约束 + 问题 A
第二次：项目约束 + 问题 A + 回答 A + 问题 B
第三次：项目约束 + 问题 A + 回答 A + 问题 B + 回答 B + 问题 C
```

相邻请求的前半段往往重复。Prompt caching 就能在符合条件时复用这些前缀的计算结果，降低重复输入的处理开销。以 Claude API 为例，缓存命中要求相应前缀完全一致，还受缓存配置、最小长度和有效期等条件影响。不是每次请求都会自动命中，也不是把最新一句话换种说法，就一定失去此前所有前缀的命中。[Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)

故事中的“旧页印记”借喻的就是计算复用。旧页仍然在这次卷宗里，只是不用付出同样的重复处理成本。

关键限制也在这里：**命中的内容仍然占用上下文窗口。** Claude 的文档明确把缓存读取、缓存写入与普通输入都计入窗口。缓存没有把一大册历史变成无限容量，也没有替你判断哪条决定已经失效。[上下文与缓存计数](https://platform.claude.com/docs/en/build-with-claude/context-windows)

于是，完整回放仍然会遇到故事里的三个问题：

- **装不下**：对话和工具结果不断增长，最终需要截取、压缩或按需取用。
- **重点难找**：重复信息、废弃方案和当前要求混在一起，不能保证模型总能用对。
- **换一件事就得重新挑资料**：哪个项目、哪个用户的记录该带上，需要应用决定。

缓存值得利用，却不能替我们完成这些选择。下一步要做的，就是像小满那样管理记录：什么始终带着，什么临时去查，什么已经作废。

## 4. Memory 开始负责选择与维护

故事里，小卡、原始工单和页码共同构成了记忆机制。小卡保留当前需要的信息，工单保存细节，页码让人能回查依据。把小卡改了又改、核对旧规格的工作，则是维护记忆的代价。

落到 Agent 中，可以把这几件事分开：

| 环节 | 要做的事 |
| --- | --- |
| 记录 | 保留原始交互，提取值得复用的事实、偏好或决定 |
| 组织 | 标明来源、时间、所属用户或项目，区分原文和推断 |
| 找回 | 为当前任务选择相关内容，通过加载、搜索或工具读取提供给模型 |
| 维护 | 更新旧决定、纠正错误、处理过期和删除，避免矛盾一直累积 |

这些内容最终仍然要进入模型能使用的上下文。Memory 改变的是上下文从哪里来、怎样选择和维护，并没有另开一条绕过模型输入的通道。

为了具体看实现，我们换成一个开发中的例子：用户确认“这个项目第一版使用本地文件，暂时不接云服务”。以后 Agent 再设计数据存储时，应该找回这条决定；如果第二版改变了方向，又应该使用更新后的要求。

```text
确认决定 → 保存内容及来源
                 ↓
新任务 → 找回当前相关且有效的记忆 → 组装上下文 → 模型与工具执行
                 ↑                                      ↓
                 └──────── 记录新信息、更新旧状态 ─────────┘
```

收益是不用每次重放整个项目的历史，代价是多了提取、检索和维护。摘要可能遗漏否定词，搜索可能找错项目，写入也可能把推断当成事实。记忆系统本身需要被检查。

它和缓存还会相互影响：频繁重写输入前部的记忆，可能破坏原本稳定的缓存前缀。常见安排是保留稳定前缀，把变化的检索结果放在后面；具体顺序仍须遵守所用 API 的消息规则和缓存方式。因此，压缩得更短与缓存命中更多，需要结合实际开销权衡。[缓存前缀安排](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)

寓言用一面镜子和一位学徒简化了这些分工。实际系统里，保存可以由程序完成，提取可以交给模型，读取可以由工具触发，也可以在调用前自动进行。下面的四家实现，正好给出了不同的答案。

## 5. 同一句“记住它”，四种实现

### 5.1 OpenClaw：先把记忆写到能打开的文件里

如果那条决定被写成 Markdown，你就能直接打开它，确认 Agent 到底保存了什么。

OpenClaw 的文件记忆采用这种可见的形式：`MEMORY.md` 保存精炼的长期内容，`memory/` 下的日期笔记保留更具体的过程记录。Agent 在工作中记录信息，压缩前保存重要内容；后续的 dreaming 整理再把符合条件的记录提炼进长期层。[OpenClaw Memory](https://docs.openclaw.ai/concepts/memory)

这给了我们两种不同的阅读方式：少量重要信息随上下文加载，更详细的内容在需要时通过 `memory_search`、`memory_get` 等工具查找和回读。内置搜索引擎使用 SQLite，并可组合关键词与向量检索。[内置记忆引擎](https://docs.openclaw.ai/concepts/memory-builtin)

放回例子里，“第一版使用本地文件”可以成为长期决定，而讨论过程留在具体记录中。下一次需要解释“为什么没有选云数据库”，再沿来源回查，不必始终带着整段争论。

我最想借鉴的是这种分层：**人能查看的记忆内容，与帮助系统找到内容的索引，各有职责。**

不过，不能据此推断 OpenClaw 的全部数据库内容都只是可丢弃索引。当前实现还保存来源元数据、部分意图及整理状态。本文借鉴的是文件记忆思路，自己的简化方案需要另行确定边界。[记忆架构](https://docs.openclaw.ai/concepts/memory-architecture)

文件让记忆容易检查，但并没有自动解决“启动时应该读多少”的问题。Claude Code 的做法，能进一步说明这个选择。

### 5.2 Claude Code：把入口放在眼前，把细节留在文件里

Claude Code 区分两类内容：`CLAUDE.md` 承载人为维护的项目指令；auto memory 则由 Claude 根据交互判断什么值得留给未来，例如用户纠正、偏好和项目背景。它并不要求每个会话都写一条记忆。[Claude Code Memory](https://code.claude.com/docs/en/memory)

自动记忆目录里，`MEMORY.md` 充当入口，具体内容放进主题文件。启动时加载入口的有限部分，详细文件按需读取。用户也可以直接编辑和删除这些 Markdown 文件。

这像是为下一次会话留下“该去哪里看”的线索。前面的存储决定如果是必须长期遵守的项目要求，可以由人明确写进项目指令；如果作为交流中积累的项目背景保存，则需要检查自动记忆实际写下了什么。

两种方式都在提供上下文，但写入责任不同。尤其不能把“我已经说过”直接等同于“它一定写进了自动记忆”。

由此又出现一个问题：如果我希望自己决定记录和加载规则，运行框架需要提前替我做完多少？

### 5.3 pi Agent：会话已经能保存，长期记忆仍可以自己定义

pi 默认提供 `read`、`write`、`edit`、`bash` 四个工具。它也会保存会话，支持恢复，以及对长会话做压缩；压缩用于缩短当前上下文，完整历史仍保留在 JSONL 会话文件中。因此，说 pi“完全没有记忆”会漏掉它已经提供的连续性能力。[pi 官方说明](https://github.com/badlogic/pi-mono/blob/main/packages/coding-agent/README.md)

但恢复一段会话，与跨会话自动挑出长期决定，仍然有距离。记录在文件中，不意味着新会话会自动发现它。

pi 的扩展接口允许订阅生命周期事件、增加工具、注入上下文和定制压缩。这样就可以构建自己的路径：通过一个扩展保存项目决定，再在相关请求中查找、读入。这个路径是可以实现的设计示例，并非 pi 默认就替你运行的长期记忆流程。[扩展文档](https://github.com/badlogic/pi-mono/blob/main/packages/coding-agent/docs/extensions.md)

这里值得学习的是能力之间的边界。文件工具解决“能不能读写”，会话系统解决“能不能恢复”，扩展再决定“什么值得跨会话使用”。获得控制权的同时，记录规则和召回质量也需要自己负责。

Mastra 则把其中不少职责做成了可以配置的独立能力。

### 5.4 Mastra：拆开保存、提炼、召回与压缩

我当前使用的是 Mastra。它的 Memory 最适合拆开来看，否则很容易把几种能力都理解成“框架帮我记住了”。

| 能力 | 在读写链路中的职责 |
| --- | --- |
| Message History | 持久保存消息，并为调用提供近期历史 |
| Working Memory | 维护持续相关的用户或任务信息 |
| Semantic Recall | 从历史消息中检索与当前输入相关的内容 |
| Observational Memory | 把增长的历史整理成更紧凑的观察记录 |

这些能力可以按需求启用，数据通过配置的存储适配器保存；启用一种，也不代表自动获得所有其他能力。[Mastra Memory](https://mastra.ai/docs/memory/overview)

**Message History 回答“我们聊过什么”。** 它能让同一会话继续，但如果只取近期消息，早期决定仍可能离开本次上下文。

**Working Memory 回答“哪些信息应该持续在场”。** 常见路径是主 Agent 调用 `updateWorkingMemory` 工具更新一块 Markdown 或结构化数据，也可以由程序更新，或按配置交给 Observer 维护。它能按 thread 隔离，也能按 resource 跨会话保留；这里的 resource 常用于表示同一个用户或实体。[Working Memory](https://mastra.ai/docs/memory/working-memory)

在我们的例子里，可以把当前项目约束维护成一小块状态。但如果把项目 A 的决定保存成用户全局偏好，再用于项目 B，即使记住的句子没错，也会用错地方。作用域也是记忆含义的一部分。

**Semantic Recall 回答“以前哪段话与现在有关”。** 它借助 embedding 和向量检索匹配历史消息，也可以带回相邻消息，补足上下文。这里的关键是检索，而不是自动把所有历史提炼成一份事实清单。[Semantic Recall](https://mastra.ai/docs/memory/semantic-recall)

**Observational Memory 回答“对话已经很长，怎样继续”。** Observer 把历史整理为观察记录；观察记录继续增长后，Reflector 再做整合与压缩。这些内容替代一部分原始历史进入模型上下文，触发由 token 预算等配置控制。[Observational Memory](https://mastra.ai/docs/memory/observational-memory)

这种做法能降低长期携带原文的负担，但总结仍要保留真正影响行动的内容。如果把“暂时不接云服务”缩成“讨论云服务”，压缩成功了，约束却消失了。

到这里，四种实现已经把问题拆开：文件在哪里只是一个维度；更关键的是，谁负责把信息从过去带到现在，中途如何选择和加工。

## 6. 也可以把 Memory 单独做成一层

前面看的，有完整 Agent 产品，也有开发框架。还有一条路线，是把 Memory 做成可以单独接入的组件。

**Mem0** 提供记忆添加与查询等接口。应用把交互内容交给它，在启用提取的路径中生成适合后续使用的记忆，再按用户等标识查询相关内容。它同时提供开源实现与托管服务，需要区分各自范围。[Mem0 添加记忆](https://docs.mem0.ai/core-concepts/memory-operations/add)、[开源仓库](https://github.com/mem0ai/mem0)

应用仍要决定什么时候调用这些接口，以及如何把查询结果交给模型。独立组件提供了一段读写流程，并不会仅凭安装就知道整个 Agent 的任务边界。

**Graphiti** 把信息组织为带时间的实体和关系，并保留到来源记录的追溯。比如项目最初选择本地存储，后来决定迁移云服务：除了找出两条相似文本，还可以表达关系如何变化、哪个事实在何时有效。[Graphiti 官方仓库](https://github.com/getzep/graphiti)

这给我们增加了一个观察角度：有些记忆主要帮助找回原话，有些要维护精炼状态，还有些需要表达随时间变化的关系。它们对数据组织和维护提出的要求不同。

所以，参考其他开源方案时，我更关心它补上了哪一段能力，以及接入以后自己仍要做什么。项目名称和功能列表不能代替这两个问题。

## 7. 把不同实现放回同一组问题里

回看这些系统，可以得到一张简表。这里比较的是前面讨论的主要机制，不是完整功能清单。

| 实现 | 保存与维护的重点 | 如何回到上下文 | 值得借鉴什么 |
| --- | --- | --- | --- |
| OpenClaw | 文件记录、长期精选与整理流程 | 入口加载、搜索和回读 | 内容分层与来源回查 |
| Claude Code | 人为指令、自动记忆入口与主题文件 | 启动加载入口、按需读细节 | 写入责任与加载预算 |
| pi Agent | 会话持久化、压缩、可扩展的记忆规则 | 恢复会话，或由扩展组织读取 | 基础能力与自定义策略的边界 |
| Mastra | 历史、持续状态、语义召回、观察记录 | 按启用能力组装上下文 | 把不同职责分别配置 |
| Mem0 | 独立的记忆写入与检索组件 | 接入方取回结果并提供给模型 | 将记忆能力接到不同应用 |
| Graphiti | 带时间与来源的实体关系 | 查询图中的相关上下文 | 表达事实的变化与关系 |

如果今天要判断一个新的 Memory 实现，我会沿着一条信息追问：它写进了哪里？保存的是原话还是推断？什么时候读取？属于哪个用户或项目？旧决定被替换后，下一次还会不会读到旧版本？

这些问题也解释了为什么“记住越多越好”不够准确。

我们的例子里，暂时不接云服务是第一版的约束。到了第二版，用户可能明确要求迁移。如果系统只不断追加，新的要求和旧的限制就会一起出现。保留历史有价值，但当前决策还需要知道哪条仍然有效。

同样，摘要变短、向量命中、文件写入成功，都只是链路中某一步的结果。最终要观察的是：Agent 有没有在合适的任务里使用正确的信息。

## 8. 我想从一份能打开的记忆开始

看过这些做法，我自己的实现方向更清楚了：先参考 OpenClaw 的文件思路，把记忆保存成能直接阅读、编辑和带走的内容；SQLite、全文和向量索引承担可重建的检索工作。

这样，当 Agent 再次忽略那条项目约束时，我至少可以沿着路径检查：文件里有没有？索引是否更新？检索有没有找到？本次上下文有没有带上？

为了做到这一点，来源、适用范围和有效状态也需要随着记忆保留下来。仅把正文写成 Markdown，却把决定含义的唯一元数据留在数据库里，还不能兑现“从文件重建”的目标。

这条路线也意味着，我需要自己处理文件组织、写入一致性、更新删除和召回。Mastra 仍然可以负责 Agent 的运行，记忆层则通过明确的接口接进去。

再回到修车铺。镜子提供判断，小满接起行动与反馈，工单和小卡保留可以再次使用的经历。换成 Agent，同样需要让模型的推理、harness 的执行，以及 Memory 对信息的维护配合起来。

下一篇就从这里开始：明确自己的 Memory 要记住什么、怎样组织和读写，以及做到什么程度，才足够支持持续工作。
