# 构建跨 Agent 的通用 Memory

> [!note]
> Claude Code 有 Claude Code 的记忆，Codex 有 Codex 的记忆，pi 默认没有记忆，OpenClaw 又是一套。用得越久越清楚一件事：记忆跟着工具走，人就跟着被工具绑架。这一篇参考 OpenClaw 官方的 Memory 设计，给"同一个记忆目录、所有 Agent 共用"画一张可落地的设计图，重点讲三件最容易被忽略的事：import、export 和拦截。

## 1. 先看 OpenClaw 的 Memory 是怎么设计的

OpenClaw 是目前把"文件优先的 Agent 记忆"做得最完整的参考实现。它的官方文档里有一个反复出现的原则：

> 真相（truth）是普通 Markdown；SQLite 只是索引，随时可以重建。

目录结构长这样：

```
~/.openclaw/workspace/
├── USER.md              # 指令画像：用户希望 Agent 怎么对待自己
├── MEMORY.md            # 长期记忆精选：注入上下文的主入口，有预算上限
├── memory/
│   ├── 2026-09-01.md    # 工作层：按天的日志，只建索引不注入
│   ├── imports/         # 从其他 Agent 导入的记忆，按来源隔离
│   └── .dreams/         # "做梦"整理的暂存区
└── DREAMS.md            # 做梦产出的变更报告，供人审阅
```

配套机制：

| 机制 | 做法 |
| --- | --- |
| 检索 | `memory_search` / `memory_get` 工具，BM25 关键词 + 向量混合搜索，走 SQLite 索引 |
| 索引 | 索引坏了就 `openclaw memory index --force` 重建，Markdown 永远是真相 |
| 做梦（dreaming） | 定时任务整理记忆：有分数门槛、有召回频率门槛，改动可回滚，产出进 DREAMS.md 供人审 |
| 导入 | 从 Claude Code / Codex 迁移时**只复制 Markdown**，隔离存放，不合并、先备份、出报告 |
| 动作敏感记忆 | 涉及授权、有效期、权限边界的记忆单独标记，使用前要确认 |
| 压缩前落盘 | 上下文要压缩（compaction）前，先把工作记忆 flush 到文件，防止丢失 |

注意一个容易被看反的细节：**OpenClaw 做了 SQLite，但仍然是文件优先**。数据库是缓存，不是真相。这是整个设计里最值得抄的一条。

## 2. 从中提炼四条可迁移的原则

### 2.1 Markdown 是互操作格式

SQLite、向量库、任何专用格式都会把记忆锁死在某一个工具里。所有 Agent 都能读的东西只有一种：放在目录里的 Markdown 文件。

### 2.2 真相层和索引层分离

- 真相层：人和 Agent 都能直接读写的 Markdown
- 索引层：为检索性能服务的衍生数据，删了能重建

索引层可以按 Agent 各建各的（OpenClaw 用 SQLite，Claude Code 有自己的索引），只要它们都从同一份 Markdown 派生，就不存在锁定。

### 2.3 读容易，写要分层

多 Agent 共写同一个文件是灾难的开始。解法是分层写入：

- **追加层**：谁都可以往自己的日志文件追加，互不冲突
- **蒸馏层**：只有一个写入者（单一 writer），定期从追加层提炼

### 2.4 每个 Agent 有自己的引导挂载点

记忆本体放一份，但每个 Agent 启动时读的入口文件不同。入口文件里不写记忆，只写"记忆在哪、怎么用"。

## 3. 通用 Memory 目录的设计

把上面四条原则落成一个具体结构：

```
~/memory/
├── MEMORY.md            # 蒸馏层：长期记忆精选（单写手维护）
├── journal/
│   ├── claude/2026-09-01.md   # 追加层：按 Agent 来源隔离的日志
│   ├── codex/2026-09-01.md
│   └── pi/2026-09-01.md
├── imports/
│   └── openclaw/        # 从其他系统导入的记忆，按来源隔离
├── distill-log.md       # 每次蒸馏的记录：日期、来源、变更
└── index/               # 可重建的索引（SQLite / 向量库），删了不影响真相
```

然后给每个 Agent 接上自己的引导文件：

| Agent | 引导挂载点 | 内容 |
| --- | --- | --- |
| pi | `~/.pi/agent/AGENTS.md` | 指向 `~/memory`，写明读写规则 |
| Codex | `~/.codex/AGENTS.md` | 同上 |
| Claude Code | `~/.claude/CLAUDE.md`（或项目 CLAUDE.md `@` 导入） | 同上 |
| OpenClaw | workspace 本身就是记忆目录 | 可直接把 `~/memory` 挂进去 |

引导文件里只写两类内容：记忆目录的路径、使用纪律（日志往哪追加、什么不许写、敏感内容怎么处理）。**记忆本身永远不复制进引导文件**，否则马上出现多份不同步的副本。

顺带说一句：AGENTS.md 正在成为跨 Agent 的事实标准，pi、Codex、Claude Code 都认。本仓库根目录的 AGENTS.md 用 CLAUDE.md `@` 导入，就是这套挂载方式的一个现成实例。

## 4. Import：复制，而不是合并

换工具、或想吸收另一个 Agent 的记忆时，最容易犯的错是直接合并进主记忆。OpenClaw 的导入纪律值得照抄：

1. **只复制 Markdown**。数据库、缓存、会话记录不带过来。
2. **按来源隔离**。导入物放在 `imports/<来源>/`，建索引可以搜到，但不合并进 MEMORY.md。
3. **先备份，后导入，出迁移报告**。导入了什么、跳过了什么、为什么，写成一份文件。

为什么要隔离而不是合并：

- 导入的记忆没有经过本系统的蒸馏纪律，质量未知
- 两边可能对同一事实有冲突记录，直接合并等于让冲突静默生效
- 隔离存放让你可以先检索、观察一段时间，再决定哪些值得手动提升进蒸馏层

## 5. Export：从记忆里拿什么出去

Export 不是备份整个目录，而是生成一份**面向消费的只读快照**。典型场景：把记忆交给一个新 Agent、一份产品、或一次性的分析任务。

一份好的导出包含：

| 内容 | 形式 |
| --- | --- |
| 用户偏好与事实 | Markdown + YAML frontmatter（`type` / `updated` / `privacy`） |
| 项目状态卡 | 每个项目一节：目标、状态、下一步 |
| 隐私分级 | 借鉴 OpenClaw 的 `privacyTier`：`public` / `local-private` / `sensitive`，非 public 的默认不进导出 |

两条纪律：

- 导出永远从蒸馏层生成，不从原始日志生成——日志里全是过程噪音
- 导出物是快照，单向、一次性，不接受回写。要回流就走 import 流程

## 6. 拦截：在记忆进出 Agent 的路上设卡

"拦截"是通用记忆里最容易被忽略、但决定系统会不会烂掉的部分。三个拦截点：

### 6.1 读侧拦截：控制什么进入上下文

- MEMORY.md 设注入预算（OpenClaw 的做法是超预算截断并提示），防止记忆膨胀吃掉上下文
- 按隐私分级过滤：`sensitive` 的内容默认不注入
- 不同 Agent 可以看到不同的视图——引导文件里声明这个 Agent 的可见范围

### 6.2 写侧拦截：控制什么被写进记忆

- **追加层放开**：各 Agent 往自己的 journal 文件追加，无需审批
- **蒸馏层锁死**：只有单写手（一次显式的"同步记忆库"操作）能改 MEMORY.md
- **动作敏感记忆单独标记**：授权、密码、权限边界这类内容，写入时要确认、使用时要检查有效期
- **压缩前 flush**：Agent 上下文要压缩前，先把有价值的工作记忆落盘，这是 OpenClaw 踩过坑后加的机制

### 6.3 审计层：git 就是回滚和追责

真相层放进 git 仓库：

- 每次蒸馏是一个 commit，谁能改、改了什么，一目了然
- 蒸馏出错就 revert，对应 OpenClaw dreaming 的回滚机制
- 不需要自建任何审计系统

## 7. 和本仓库 LLM Wiki 的关系

这套设计不需要从零建。本仓库已经是一个实例，只是分层稍有不同：

| 通用设计 | 本仓库的对应物 |
| --- | --- |
| 真相层（Markdown） | `obsidian/` 原始笔记，人类所有 |
| 蒸馏层（单写手） | `wiki/`，由一次"同步记忆库"操作增量维护 |
| 追加层（journal） | 平时直接在 obsidian/ 写新笔记 |
| 引导挂载点 | 根目录 AGENTS.md（被 CLAUDE.md 导入） |
| 拦截-写侧 | "加载记忆只代表读取"“不自动删除”“待核实"标注 |
| dreaming | "同步记忆库"工作流本身 |

换句话说：如果要做通用 memory，最省事的路径不是新建 `~/memory`，而是把本仓库当真相层 + 蒸馏层，再给每个 Agent 写好各自的引导文件。缺的只是 journal 隔离和 privacy 分级两块，可以后补。

## 8. 这篇先记住五个结论

1. 真相是 Markdown，索引（SQLite / 向量）只是可重建的缓存——这是 OpenClaw Memory 最核心的一条设计。
2. 写入分两层：日志层按来源隔离随便追加，蒸馏层只有单写手。
3. Import 只复制、按来源隔离、先备份出报告，永远不要直接合并。
4. Export 是从蒸馏层生成的只读快照，带隐私分级，单向不回写。
5. 拦截发生在三个点：读侧（预算和隐私过滤）、写侧（分层和敏感标记）、审计（git 回滚）。
