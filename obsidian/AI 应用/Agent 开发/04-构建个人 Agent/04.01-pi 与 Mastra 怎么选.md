# pi 与 Mastra 怎么选

> [!note]
> 想做自己的 Agent 时，第一个卡住的问题往往不是"怎么写代码"，而是"在什么上面写"。pi 和 Mastra 是两个经常被放在一起比较的项目，但它们其实不在同一条赛道上竞争。这一篇把两者的真实差异讲清楚，并回答一个比喻：pi 是发动机和原型车，Mastra 是自己做了一辆车，是这样吗？

## 1. 为什么这个问题容易让人糊涂

围绕这两个项目，流传着几种说法：

- "本地用 pi，线上用 Mastra"
- "Mastra 底层可以用 pi"
- "Mastra 接了 Vercel AI SDK，是个完整的 Agent Runtime"

这三种说法都不准确，或者只对了三分之一。根源在于：pi 和 Mastra 的分层方式不一样，拿它们当同类产品对比，就像拿"发动机制造商"和"汽车厂"比谁的车好。

先把结论放在前面：

| 项目 | 本质 | 一句话定位 |
| --- | --- | --- |
| pi | 自包含的 Agent 引擎 + 一辆能直接开的原型车 | 把 Agent Loop 做到极小、极透明，其余全部用 TypeScript 扩展 |
| Mastra | 面向服务端的 Agent 应用框架（造车平台） | 假设你要运营 Agent 服务，把工程化能力整套给你 |

## 2. pi 在解决什么问题

pi 出自 Mario Zechner（badlogic），现在是 Earendil 维护的开源项目，MIT 协议。它的设计哲学是：Agent 的核心其实很小，别把核心藏起来。

拆开看是几个包：

| 包 | 职责 |
| --- | --- |
| `@earendil-works/pi-ai` | 统一的多 Provider LLM API，一套接口接十几家模型 |
| `@earendil-works/pi-agent-core` | Agent Loop 和会话状态，循环本身就是库 |
| `@earendil-works/pi-coding-agent` | CLI 产品，一个可以直接用的编码 Agent |
| `pi-tui` / `pi-telemetry` | 终端 UI 和遥测 |

几个关键数字和事实：

- 内置工具只有 4 个（read / write / edit / bash），系统提示词不到 1000 token
- 其他一切能力都是 TypeScript 扩展，不进核心
- 4 种使用形态：交互式 TUI、print 模式、RPC over stdio、SDK 内嵌
- 会话是 JSONL 树，上下文文件用 AGENTS.md / SYSTEM.md
- 没有内置权限系统（要隔离就容器化），也没有内置长期记忆（要用扩展补）

OpenClaw 就是把 pi 当 SDK 内嵌使用的参考实现。

## 3. Mastra 在解决什么问题

Mastra 是一个 TypeScript 服务端 Agent 框架。它假设的场景是：你要把 Agent 当成一个长期运营的产品——多用户、多 Agent、要部署、要观测、要评测。

它直接内置了一整套：

| 能力 | Mastra 的做法 |
| --- | --- |
| 模型接入 | 自带 Model Router，`model: "anthropic/claude-4-5-sonnet"` 字符串直用，读环境变量 |
| Agent Loop | 自研实现，不依赖外部循环库 |
| Memory | 语义记忆、工作记忆、观察记忆分层 |
| 工程化 | Durable Workflows、RAG、Evals、可观测性 |
| 存储 | Postgres / LibSQL / MongoDB |
| 调试 | Mastra Studio（localhost:4111） |
| 部署 | Cloudflare、Mastra Platform |

两个容易误传的技术事实：

1. **Mastra 底层不是 pi。** Mastra 的 SDK agents 列表里有 `@mastra/claude`、`@mastra/cursor`、`@mastra/openai`，没有也不需要 `@mastra/pi`。两者的 Agent Loop 是各自独立实现的。
2. **Mastra 不是建立在 Vercel AI SDK 之上。** 看 npm 依赖就知道：`@mastra/core` 只依赖 `@ai-sdk/provider` 系列的**类型契约包**，不依赖 `ai` 运行时。模型路由是 Mastra 自研的；`@mastra/ai-sdk` 的 `withMastra()` 反而是给 AI SDK 应用接入 Mastra 的互操作层，方向是反的。

## 4. 用四层视角对齐两者

把两个项目放到同一张分层图上，差异立刻清晰：

| 层 | pi | Mastra | Vercel AI SDK（参照物） |
| --- | --- | --- | --- |
| 模型层 | `pi-ai` 统一 API | 自研 Model Router | 本体就是这层 |
| 循环层 | `pi-agent-core`，极简可读 | Mastra Agent，自研 | `generateText` + maxSteps |
| 工程层 | 扩展机制，轻 | Memory / Workflows / RAG / Evals，重 | 基本不管 |
| 产品层 | pi CLI（原型车） | Studio + Platform + 部署 | 无 |

所以"本地用 pi、线上用 Mastra"这句流传的话，更准确的说法是：

> pi 和 Mastra 的差异轴不是"本地 vs 线上"，而是**引擎 vs 基础设施**。pi 给你发动机和一个能开的原型车；Mastra 给你一条造车产线，并假设你要造的是车队。

## 5. 回到那个比喻：发动机、原型车和造车平台

"pi 是发动机和原型车，Mastra 是自己做了一辆车"——方向是对的，但有两处要修正：

### 5.1 pi 的部分基本准确

pi 确实是"发动机制造商 + 一辆原型车"：

- 发动机 = `pi-ai` + `pi-agent-core`，你可以只拿引擎，装进自己的壳里
- 原型车 = pi CLI，开箱能开，还能当参考实现读源码

### 5.2 Mastra 不是"自己造了一辆车"

更准确的比喻是**造车平台 / 整车厂底盘**：

- 它不是某一辆车，而是"假设你要批量造车、运营车队"的一整套产线：底盘（Agent + 模型路由）、车队管理（多 Agent）、维修记录（Trace + Evals）、门店（Studio + 部署）
- 如果你要造的是"一辆自己的自用车"（本地个人 Agent），这条产线的大部分设备用不上，反而要按产线的规矩改装你的车

## 6. 什么情况选 pi

- 做本地个人 Agent，或者往 Electron 桌面应用的主进程里嵌 Agent（SDK 形态）
- 想自己掌控 UI 和交互，只缺一个透明可靠的循环引擎
- 希望核心足够小，能读完、能改懂、能自己扩展
- 接受两件事自己补：权限隔离（容器化解决）、长期记忆（扩展解决）

## 7. 什么情况选 Mastra

- 做**服务端**的 Agent 产品，尤其是多用户、多 Agent 的场景
- 直接需要 Memory、RAG、Durable Workflows、Evals、可观测性这一整套，不想自己拼
- 要部署到 Cloudflare 或自己的服务器，用 Studio 可视化调试
- 团队协作，需要框架级别的约定

一句话决策：

> 造**一辆自己的车**，用 pi；开**一家运营车队的公司**，用 Mastra。做个人 Agent 几乎总是前者。

## 8. 这篇先记住五个结论

1. pi 和 Mastra 不在同一层竞争：一个是 Agent 引擎（附带原型车），一个是服务端应用框架（造车平台）。
2. "本地 pi、线上 Mastra"的准确版本是"引擎 vs 基础设施"，跟部署位置无关。
3. Mastra 底层不是 pi；两者各写各的 Agent Loop。
4. Mastra 也不是建立在 Vercel AI SDK 之上，只用了它的 Provider 类型契约，模型路由是自研的。
5. 个人 Agent、桌面内嵌 Agent 选 pi；服务端多用户 Agent 产品选 Mastra。
