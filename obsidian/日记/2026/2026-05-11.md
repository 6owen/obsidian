## ai skill 技能设计

从工具依赖到工作流重构

最近在整理关于 AI 编码工具（如 Superpowers, GStack, OpenSpec 等）的思考。在体验了众多产品后，我愈发意识到：与其追求某种“全能”的单一工具，不如将精力投入到构建属于自己或团队的 Research、Design、Plan、Develop、Test 和 Commit 工作流中。
早在一年前，当 Cursor（Kiro）刚开始火热、模型能力尚未达到如今高度时，社区就提出了“Spec（规范驱动）”的观点。如今看来，这个观点不仅没有过时，反而成为了 Agent 工作的默认环节，只是在实现形式上需要随着模型的迭代进行适配。

1. 警惕“一键编程”的噱头，回归工作流本质
   每当主流模型更新，市场上总会有“程序员要失业”、“一键干掉编程”的宣传噱头。但在真实的团队开发场景中，这些往往只是空中楼阁。
   目前最有价值的方向，依然是工作流（Workflow）的 Skill 化建设。我们需要的是可控、高质量、团队化的代码 Agent。
   这里存在一个有趣的悖论：当模型能力尚弱时，像 Superpowers 这样提供精细化约束的工具非常高效；但随着模型能力的爆炸式增长，过于僵化的工作流反而会限制模型的发挥。如何在“确定性的约束”与“模型自主性”之间找到平衡，是目前探索的核心局限与挑战。

2. 角色分工的虚与实
   过去业内热衷于炒作 AI 的“三省六部制”或“多角色分工”。但在实际生产中，我发现给 AI 设置固定角色的最大收益并非“能力突变”，而是上下文隔离（Context Isolation）。
   单纯靠一个 Roleplay Prompt 并不能让模型产生质变的能力，核心依然取决于底座模型。因此，与其在“角色名”上浪费时间，不如将重点放在**技能组（Skill Set）**的沉淀上——即如何将思考、设计、审查、调试和验证这五大步骤细化。

3. 深度思考：如何让模型不再“和稀泥”？
   在“思考”阶段，核心目标是达成团队共识。但简单的 Supervisor 模式（几个 Sub-agent 脑风暴后选最优解）往往收效甚微。
   模型天生倾向于“不表态”，像投资建议一样只给参考。为了让最强的模型执行得更好，我们需要在 Prompt 层面施加压力：
   立场强制化：要求模型必须有明确立场，并清晰说明“什么证据能推翻该立场”。
   决策多样性：除了给 2-3 个选项，必须包含一个“最小化实现选项”，且必须给出明确推荐。
   自律反驳机制：方案产出后，要求模型进行“自我抨击”。在什么情况下方案会失效？如果能修复，则补充进方案；如果无法修复，必须直白告知风险。这种“心知肚明”的方案，才是人类开发者敢于采纳的。

4. 设计阶段：防止在错误的前提下狂奔
   “设计”不只是写代码，它应该包含前置验证。
   路径验证：AI 经常在错误的目录路径上反复修改。设计阶段必须先锁定文件位置，查阅旧的技术方案文档，避免重复造轮子。
   外部调研：通过 Web Search 或 GitHub 检索，确保设计不是建立在过时信息或错误前提之上。
   复杂性分级：
   如果涉及超过 8 个文件的变动，必须明确告知规模。
   如果涉及 3 个以上组件的数据交换，必须画出 ASCII 拓扑图以排查循环依赖。
   在方案阶段列清所有第三方依赖，防止白忙一场或引入不靠谱的库。

结语：思考优于编码

我始终认为，思考和设计层面绝不应轻易动笔写代码。
一个成熟的代码 Agent 工作流应当是：做什么、不做什么、选哪个方案、理由是什么、有哪些未知项。这 3-5 个决策依据清晰且经过批准后，再进入编码环节。
从简单归纳法到精细的工作流设计，AI 编程的未来不在于它能写多快，而在于它能想多深。
