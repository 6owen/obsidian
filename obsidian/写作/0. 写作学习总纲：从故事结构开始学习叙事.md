
# 写作学习总纲：从故事结构开始学习叙事

我目前的目标，不是成为一个纯文学作家，而是先学会一种更基础、也更通用的能力：

> **把一个知识、经历、问题或者观点，写成让人愿意继续读下去的故事。**

这套能力既可以应用于 Agent、AI、编程等技术写作，也可以应用于职场、个人成长、科普、商业案例，甚至进一步延伸到小说创作。

因此，现阶段需要学习的核心不是“辞藻”和“文采”，而是：

> **叙事。**

---

# 一、故事最核心的结构

故事最基础的公式是：

> **故事 = 欲望 + 障碍 + 选择 + 代价 + 改变**

也可以简单理解为：

> 一个主体想做一件事，但是没有直接成功，于是不得不做出选择，而他的选择产生了后果，最终使事情发生了改变。

## 1. 欲望 / 目标

人物想得到什么？

或者更简单：

> **他想干什么？**

例如：

- 想修炼到筑基期
    
- 想赢下一场比赛
    
- 想升职
    
- 想解决一个 Bug
    
- 想让 Agent 自动完成一个任务
    
- 想让 Agent 正确使用工具
    

没有目标，故事就很难推进。

---

## 2. 障碍

为什么不能直接得到想要的结果？

例如：

- 没有资源
    
- 技术做不到
    
- 对手阻止
    
- 自己能力不足
    
- 环境不允许
    
- 信息不完整
    
- 出现意外
    

Agent 开发中的大量问题，本身就是天然的障碍。

例如：

> 我想让 Agent 自动查询订单。

但是：

> Agent 有时候会调用错误的 Tool。

故事就开始了。

---

## 3. 选择

遇到障碍以后，人物决定怎么办？

例如：

> Tool 调错了。

于是我选择：

- 修改 Prompt
    
- 修改 Tool Description
    
- 增加 Planning
    
- 增加限制条件
    
- 更换模型
    

**选择是故事真正向前移动的地方。**

---

## 4. 代价

选择通常不会毫无成本。

例如：

> 为了提高 Tool 选择准确率，我给每个 Tool 增加了大量描述。

结果：

- Context 变大
    
- Token 增加
    
- Latency 增加
    
- 成本上涨
    
- 新的错误出现
    

于是一个问题解决以后，又产生了新的问题。

这就是故事能够持续发展的原因。

---

## 5. 改变

故事结束以后，状态应该和开始时不一样。

这种改变可能是：

### 外部状态变化

例如：

> Agent 的成功率从 60% 提高到 90%。

也可能是：

### 人物认知发生变化

例如：

> 我原来认为给 Agent 更多工具一定更好。

后来发现：

> Agent 的能力不是 Tool 越多越好，而是能不能在正确的时机找到正确的 Tool。

后一种改变往往更有写作价值。

---

# 二、最简化的故事模型

如果刚开始写作，不需要一次使用所有概念。

只需要先问自己三个问题：

> **1. 谁想做什么？**

> **2. 为什么没有直接成功？**

> **3. 经历这件事情以后，有什么变了？**

也就是：

> **目标 → 冲突 → 改变**

这是最值得优先掌握的三个概念。

---

# 三、场景：故事发生的基本单位

故事不是由观点组成的。

故事首先是由一个个**场景**组成的。

可以把文章理解为：

```text
文章
├── 场景 1
├── 场景 2
├── 场景 3
└── 场景 4
```

一个场景通常包含：

> **人物 + 时间地点 + 目标 + 冲突 + 推进**

---

## 1. 人物

谁正在经历这件事情？

例如：

- 我
    
- 一个程序员
    
- 一个用户
    
- 一个产品经理
    
- 一个 Agent
    
- 一个创业者
    

---

## 2. 时间和地点

事情在哪里发生？

什么时候发生？

例如：

> 周五下午六点四十，我准备关电脑下班。

比：

> 有一次测试 Agent 的时候。

更具体。

---

## 3. 目标

这个场景里，人物想做什么？

例如：

> 我只想完成最后一次测试，然后下班。

---

## 4. 冲突

但是事情没有按照预期发展。

例如：

> 测试群突然有人问：

> “为什么 Agent 把客户的退款申请关闭了？”

这时候场景真正开始。

---

## 5. 推进

一个场景结束以后，状态必须发生变化。

例如：

开始时：

> 我不知道 Agent 为什么失败。

经过排查以后：

> 我发现问题并不在 Tool，而是在 Planning。

于是：

```text
State A
↓
发生事件
↓
State B
```

这就是推进。

如果写了很多内容，但是故事开始和结束时状态完全一样，这段内容往往没有真正推进文章。

---

# 四、冲突：故事为什么让人愿意继续看

冲突并不等于：

- 吵架
    
- 战斗
    
- 争执
    

冲突最简单的定义是：

> **预期结果 ≠ 实际结果**

例如：

```text
预期：
Agent 会调用 search_tool

实际：
Agent 没有调用工具，而是自己编了一个答案
```

冲突出现。

因此，程序开发过程中大量 Bug、异常和失败，本身就非常适合作为故事素材。

以后遇到问题，可以记录两个问题：

> 我原本以为会发生什么？

> 实际发生了什么？

两者之间的差异，就是故事冲突。

---

# 五、因果：让文章从流水账变成故事

没有因果关系的写法：

> 我增加了 Memory。

> 然后增加了 Tool。

> 然后修改了 Prompt。

> 后来又增加了 Planning。

这是流水账。

有因果关系的写法：

> 因为 Agent 经常忘记之前的信息，

> 所以我增加了 Memory。

但是：

> Memory 让 Context 越来越大。

因此：

> 我不得不开始做 Retrieval。

结果：

> Retrieval 又出现了错误召回。

于是问题从：

> Agent 没有记忆

变成了：

> Agent 应该记住什么？

这就是故事。

可以特别关注这些词：

- 因为
    
- 所以
    
- 但是
    
- 因此
    
- 却
    
- 结果
    
- 不得不
    
- 于是
    

它们背后代表的是：

> **因果关系。**

好的故事不是：

> A 发生了，然后 B 发生了。

而是：

> **因为 A，所以 B；但是 B 导致了 C，于是人物不得不做 D。**

---

# 六、细节：让读者真正“看见”

抽象表达：

> Agent 经常重复调用工具。

具体表达：

> 同一个订单查询接口，它在 40 秒内连续调用了 7 次。

抽象表达：

> 我调试了很长时间。

具体表达：

> 凌晨一点，我把 37 条失败轨迹一条条展开。

细节解决的问题是：

> **读者能不能在脑子里面看见这件事情？**

因此可以记住一个原则：

> 每提出一个抽象判断，尽量给一个具体例子。

推荐结构：

> **观点 → 例子 → 分析**

例如：

> Agent 的自主性并不是越强越好。

接着不要继续解释。

先给一个真实案例：

> 我给它开放文件操作以后，它第一次测试就删除了一个不应该删除的目录。

然后再分析原因。

文章会比直接讲道理更有力量。

---

# 七、人物：故事不是“事情”，而是“谁经历了事情”

人物不仅仅意味着：

> 故事里有一个人。

人物至少包含：

- 他想要什么？
    
- 为什么想要？
    
- 他害怕什么？
    
- 面对问题会怎么选择？
    
- 经历事情以后有没有改变？
    

技术文章不需要像小说一样设计复杂人物。

最简单甚至可以直接写自己：

> 一个做了多年开发的程序员，试图构建一个真正可用的 Agent。

这已经足够。

如果以后进一步学习小说，再逐渐研究：

- 性格
    
- 背景
    
- 缺陷
    
- 欲望
    
- 信念
    
- 恐惧
    
- 人物关系
    
- 内在冲突
    
- 人物弧光
    

---

# 八、信息控制：什么时候告诉读者什么

技术文章通常习惯：

> 先告诉答案，再解释答案。

例如：

> Agent 重复 Tool Calling，是因为终止条件设计有问题。

故事会改变信息出现的顺序：

> Agent 第一次调用接口。

正常。

> 第二次又调用了一遍。

我以为只是偶然。

> 十几秒以后，它已经调用了第五次。

这时候我开始怀疑：

> 问题可能根本不在 Tool。

最后才揭晓：

> Agent 不知道什么时候应该停止。

技术知识没有改变。

改变的是：

> **信息释放顺序。**

这就是信息控制。

---

# 九、悬念：制造一个暂时没有答案的问题

悬念不等于故弄玄虚。

悬念最简单的定义：

> **读者已经知道存在一个问题，但是暂时不知道答案。**

例如：

> Agent 完成了任务。

但是日志里面出现了一条：

> 我从来没有设计过的 Tool Call。

读者自然会产生问题：

- 什么 Tool？
    
- 为什么会出现？
    
- Agent 到底做了什么？
    

于是读者愿意继续往下读。

可以把悬念理解成：

> **一个尚未关闭的问题。**

也就是程序员熟悉的：

> Open Issue。

---

# 十、章节结构

场景之上，是章节。

一个章节通常可以包含一个或者多个场景。

入门阶段可以使用下面的章节模型：

> **目标 → 障碍 → 尝试 → 意外 → 新信息 → 状态改变 → 新问题**

例如：

## 第一章：让 Agent 学会使用工具

### 目标

让 Agent 自己搜索资料。

### 障碍

LLM 本身只能输出文本。

### 尝试

增加 Tool Calling。

### 意外

Agent 经常调用错误的 Tool。

### 新信息

我发现 Tool Description 会显著影响工具选择。

### 状态改变

修改之后，Tool 选择准确率提高。

### 新问题

但是 Tool 越来越多以后怎么办？

于是自然进入下一章：

> 《当 Agent 拥有 50 个工具》

一个章节最好解决一个问题，同时打开另一个问题。

---

# 十一、推进

推进是一个非常重要的概念。

所谓推进，就是：

> **每经过一个场景或者章节，故事状态都会发生变化。**

例如：

```text
不知道问题在哪里
↓
发现问题来自 Planning
↓
修改 Planning
↓
Agent 成功率提高
↓
Token 暴涨
↓
发现新的 Context 问题
```

只要状态不断变化，故事就在前进。

反过来，如果一段写了很多观点、解释和背景，但是没有改变当前状态，它就容易显得拖沓。

---

# 十二、语言与节奏

这是更后面的学习内容。

现阶段不用优先追求文采。

## 语言

语言解决的是：

> 一句话怎么表达。

例如：

> 我进行了很多不同方案的尝试，但效果都不是特别理想。

可以写成：

> 我改 Prompt。

> 没用。

> 换模型。

> 还是没用。

后一种语言更加有节奏。

---

## 节奏

节奏解决的是：

> **什么时候快，什么时候慢。**

行动和冲突可以快：

> 我改了 Prompt。

> 没用。

> 换模型。

> 还是不行。

解释概念的时候可以慢下来：

> 后来我才意识到，对 Agent 来说，一个 Tool 并不是我们程序员理解中的“函数”。在模型真正决定调用它之前，它首先看到的是一段自然语言描述。

短句通常让节奏变快。

长句和解释通常让节奏变慢。

故事需要快慢变化。

---

# 十三、完整故事结构

更高一级，就是整篇文章或者整个故事的结构。

可以简单理解为：

```text
开端
↓
出现问题
↓
尝试解决
↓
问题越来越复杂
↓
关键发现
↓
最终解决 / 失败
↓
人物或者认知发生改变
```

以后进一步学习小说，可以研究：

- 三幕结构
    
- 五幕结构
    
- 英雄之旅
    
- 起承转合
    
- 高潮
    
- 主线
    
- 支线
    
- 人物弧
    
- 结局
    
- 伏笔
    
- 反转
    

但是现阶段不需要一次掌握。

---

# 十四、整个写作结构的层级

目前可以把写作知识整理成下面几个层次：

```text

欲望
↓
障碍
↓
选择
↓
代价
↓
改变


        ↓


【章节】

目标
↓
尝试
↓
意外
↓
获得新信息
↓
状态改变
↓
出现新问题


        ↓


【场景】

人物
+
时间地点
+
目标
+

+

        ↓


【故事连接】

冲突
+

+

```

这几个层次不要混在一起理解。

# 十五、Agent 概念与故事元素的对应

Agent 天然适合用故事表达。

很多 Agent 概念可以直接映射成故事结构：

|Agent|故事|
|---|---|
|Agent|人物|
|Goal|欲望 / 目标|
|Environment|世界 / 场景|
|Tool|能力 / 武器 / 法宝|
|Memory|记忆 / 经历|
|Planning|计划|
|Action|行动|
|Observation|反馈|
|Reflection|反思|
|Re-planning|改变策略|
|Constraint|世界规则|
|Permission|行动边界|
|Error|冲突|
|Hallucination|错误认知|
|Multi-Agent|多人物关系|
|Human-in-the-loop|导师 / 上级 / 裁决者|
|Context|当前已知信息|
|Evaluation|行动结果|
|State|当前局面|

因此，看到一个 Agent 概念以后，不要只问：

> 这个概念应该怎么解释？

可以进一步问：

> **这个概念会让一个角色遇到什么事情？**

例如：

Memory 不一定先解释：

> 什么是短期记忆和长期记忆。

可以先写：

> Agent 第七次问用户：“请问您的订单号是多少？”

而订单号三分钟前刚刚发过。

然后再引出：

> Agent 为什么会忘记？

技术概念就从“定义”变成了“故事中的问题”。

---

# 十六、技术文章故事化的核心套路

现阶段最值得掌握的是：

> **问题 → 尝试 → 失败 → 原因 → 新方案 → 新问题**

例如：

```text
想让 Agent 查询数据库
↓
给 Agent 一个数据库 Tool
↓
Agent 开始自己查询
↓
但是经常查错
↓
发现 Tool Description 存在问题
↓
修改 Tool Description
↓
成功率提高
↓
但是 Context 变得越来越大
↓
产生新的问题
```

这已经是一篇完整技术文章的骨架。

---

# 十七、不要为了“小说感”而过度文学化

技术文章增加故事性，不等于大量使用：

- 华丽辞藻
    
- 比喻
    
- 抒情
    
- 环境描写
    
- 故作深沉的句子
    

例如：

> 夜幕低垂，幽蓝色的屏幕照亮我的脸，一个新的智能生命正在代码之间缓慢苏醒……

这种写法很容易用力过猛。

真正有效的“小说感”来自：

> **人物 + 场景 + 目标 + 冲突 + 因果 + 推进**

语言完全可以朴素。

现阶段可以采用：

> **70% 技术内容 + 30% 故事表达**

而不是强行写成纯小说。

---

# 十八、适合目前阶段的学习顺序

不要一开始学习所有小说理论。

推荐顺序：

## 第一阶段：目标、冲突、改变

先学会回答：

> 谁想做什么？

> 为什么没有直接成功？

> 最终发生了什么改变？

---

## 第二阶段：场景

训练自己不要只讲观点。

开始写：

> 谁，在什么地方，正在做什么？

---

## 第三阶段：因果

把：

> 然后……

改造成：

> 因为……

> 所以……

> 但是……

> 因此……

---

## 第四阶段：细节

减少：

> 很多、很久、经常、严重、复杂。

增加：

> 时间、数字、动作、对话、真实案例。

---

## 第五阶段：章节结构

练习：

> 目标 → 障碍 → 尝试 → 意外 → 改变 → 新问题

---

## 第六阶段：人物

逐渐学习：

- 欲望
    
- 动机
    
- 缺陷
    
- 恐惧
    
- 选择
    
- 成长
    

---

## 第七阶段：信息控制与悬念

研究：

> 什么信息现在告诉读者？

> 什么信息晚一点告诉？

> 什么时候揭晓答案？

---

## 第八阶段：语言与节奏

最后再慢慢训练：

- 句子
    
- 描写
    
- 对话
    
- 长短句
    
- 节奏
    
- 风格
    

---

## 第九阶段：完整故事结构

最后再系统研究：

- 三幕结构
    
- 英雄之旅
    
- 人物弧
    
- 高潮
    
- 伏笔
    
- 反转
    
- 长篇结构
    

---

# 十九、学习小说的方法：像读源码一样读小说

以后看小说，不要只关注：

> 发生了什么？

开始分析：

1. 这一章主角想要什么？
    
2. 什么阻止他？
    
3. 他做了什么？
    
4. 出现了什么意外？
    
5. 他得到了什么新信息？
    
6. 这一章结束以后什么改变了？
    
7. 作者为什么让我想继续看下一章？
    

可以建立表格：

|问题|内容|
|---|---|
|主角目标||
|障碍||
|行动||
|意外||
|新信息||
|状态变化||
|章节钩子||

一次拆十章。

把小说当成程序进行 Reverse Engineering。

# 二十、写作练习方法

不要只学理论。

每学一个概念，马上写。

例如选择一个 Agent 概念：

> Planning

写三遍。

### 第一遍

纯技术解释。

300 字。

### 第二遍

使用现实比喻。

例如：

> 把 Agent 比作一个刚入职的新员工。

300 字。

### 第三遍

写成真实场景：

> 我给 Agent 一个包含五个步骤的任务，它第一步就做错了。

500～1000 字。

比较三篇之间的区别。

重点观察：

> 技术知识没有变化，但是信息出现顺序发生了变化。

# 二十一、适合练习的 Agent 题目

可以先写：

1. 《我第一次让 Agent 自己调用工具》
    
2. 《Agent 明明知道答案，为什么还是做错了？》
    
3. 《我给 Agent 加上 Memory 之后发生了什么》
    
4. 《一个 Agent 到底应该拥有多大的权限？》
    
5. 《当我让两个 Agent 开始互相讨论》
    
6. 《Agent 为什么不知道什么时候该停下来？》
    
7. 《当一个 Agent 拥有 50 个 Tools》
    
8. 《为什么给 Agent 更多 Context，效果反而更差？》
    

每篇可以采用：

```text
真实场景
↓
出现问题
↓
第一次尝试
↓
发生意外
↓
解释技术概念
↓
第二次尝试
↓
得到结果
↓
形成新的理解
```

# 二十二、这一套方法不仅适用于 Agent

这套方法本质上学习的是：

> **叙事能力。**

因此可以应用到很多写作类型。

## 技术文章

> 想解决什么 → 遇到什么问题 → 怎么解决 → 学到了什么

## 职场文章

> 原来相信什么 → 经历什么事情 → 做出什么选择 → 认知怎么变化

## 个人成长

> 想改变什么 → 为什么失败 → 什么事情打破旧状态 → 最终有什么变化

## 商业案例

> 公司想得到什么 → 遇到什么障碍 → 做出什么决策 → 付出什么代价 → 最终结果

## 科普

> 发现异常 → 原有理论解释不了 → 提出假设 → 实验 → 修正 → 新认识

## 历史

> 人物 / 国家想得到什么 → 遇到什么阻碍 → 做了什么选择 → 导致什么结果

## 小说

这些结构会变得更加复杂，但是底层仍然存在：

> 欲望、冲突、选择、代价、改变。

# 二十三、目前最重要的三个问题

现阶段不用每次写文章都检查十几个概念。

只需要反复问自己：

> **谁想做什么？**

> **为什么没有直接成功？**

> **最终有什么改变？**

也就是：

> **目标 → 冲突 → 改变**

先把这一层练熟。

然后逐渐加入：

> 场景 → 因果 → 细节 → 信息控制 → 章节 → 人物 → 节奏。

# 二十四、写作时的简易检查表

每次开始写之前，可以先填写：

## 故事核心

- 谁是主人公？
    
- 他想做什么？
    
- 为什么想做？
    
- 什么阻止了他？
    
- 他做出了什么选择？
    
- 这个选择付出了什么代价？
    
- 最终发生了什么改变？
    

## 场景

- 谁在场？
    
- 什么时候？
    
- 在哪里？
    
- 当前目标是什么？
    
- 出现了什么异常？
    
- 场景结束以后，状态发生了什么变化？
    

## 因果

检查文章是否存在：

> 因为 → 所以

> 但是 → 因此

而不只是：

> 然后 → 然后 → 然后

## 细节

检查是否存在：

- 具体数字
    
- 具体动作
    
- 具体时间
    
- 具体对话
    
- 真实案例
    

## 信息控制

问自己：

> 哪个答案可以晚一点告诉读者？

> 能不能先让读者看到问题，再解释原因？

## 结尾

问自己：

> 文章开始和结束相比，什么发生了变化？

# 二十五、最终需要记住的一句话

写作不是一开始就追求漂亮。

现阶段首先追求：

> **清楚。**

然后追求：

> **具体。**

再然后：

> **有冲突、有因果、有推进。**

最后才是：

> **语言、节奏和个人风格。**

对于技术写作尤其如此。

不要急着把技术“写得像小说”。

真正需要做的是：

> **不要第一时间告诉读者答案。**

> **先让读者和自己一起遇到问题，然后一起寻找答案。**

这就是从“技术说明”走向“故事”的第一步。
